# BE-03 开发计划：卖家经营摘要与查询闭环

> 角色：开发团队负责人
> 前置状态：BE-02 已完成并通过 PM 验收；`purchase_in`、`sales_out`、`inventory_movement`、仓库维度库存和事务原子性已经具备。
> 执行原则：先 TDD 红灯，再后端实现，再编译和回归验证。Seller API 继续只暴露业务字段，不向业务端暴露数据库数字主键。

## 1. 目标和非目标

### 1.1 目标

BE-03 解决淘宝卖家 MVP 的经营摘要和查询闭环：

1. 提供 `GET /seller/summary`，让卖家能看到销售收入、采购支出、交易次数、库存数量、库存金额估算和低库存概览。
2. 在已验收契约上增强 `GET /seller/inventory-movements`，支持按商品、操作类型、时间范围、`limit/offset` 查询库存流水；默认响应结构必须继续保持 BE-02 的 list，不改成 envelope。
3. 提供按商品维度的经营汇总，至少能回答“某个商品当前库存多少、采购了多少钱、卖出了多少钱、发生了几次出入库”。
4. 所有查询必须基于当前 JWT 店铺上下文，不能通过请求参数选择 `puid`、`ouid`、`organization_id`、`person_id`、`resource_id`、`warehouse_id`。
5. 响应体只返回业务字段：`product_uid`、`warehouse_code`、`location_path`、`movement_uid`、`operation_type`、`quantity_delta`、`new_quantity`、`total_amount`、`summary` 类字段。
6. 查询接口不得破坏 BE-01、BE-02 的权限隔离和三国回归场景。

### 1.2 非目标

本轮不做：

1. 利润和成本会计的精确核算，包括 FIFO、LIFO、批次成本、税费、平台佣金、物流费。
2. 淘宝订单同步、退款、退货、盘点、报废、损耗。
3. 前端图表工作台。
4. AI 自然语言经营分析。
5. 财务总账重构。
6. 旧身份键兼容或数据库字段迁移。字段变更仍通过重建表解决。
7. 精确剩余库存成本。BE-03 使用简单历史采购加权平均成本估值，价格波动、退货、报废、批次差异导致的真实成本偏差留到后续成本核算阶段处理。

## 2. 统计口径

BE-03 必须先固定统计口径，避免测试和实现各算各的。

### 2.1 时间范围

1. 查询参数使用 `date_from`、`date_to`，格式为 `YYYY-MM-DD`。
2. `date_from` 包含当天 00:00:00。
3. `date_to` 对外语义为包含当天；实现必须使用半开区间 `< date_to + 1 day 00:00:00`，避免漏掉带小数秒的 `created_at`。
4. 不传时间范围时统计当前店铺全部历史数据。
5. 时间字段以数据库 `created_at` 为准。
6. `date_from > date_to` 返回 422。
7. 日期边界以数据库会话本地时区为准；测试环境必须确认数据库会话时区与应用测试时区均为 `Asia/Shanghai` / UTC+8。
8. TDD 不允许直接修改数据库时间。日期过滤测试使用动态日期：
   - `today = datetime.now(ZoneInfo("Asia/Shanghai")).date()`，当天范围必须命中新创建流水。
   - `date_from = tomorrow` 必须不命中新创建流水。
   - `date_to = yesterday` 必须不命中新创建流水。
9. 如果需要跨日历史数据测试，必须先由 PM 批准新增测试专用 API 或 fixture；BE-03 默认不做。

### 2.2 金额、数量和计数

1. `purchase_amount`：`inventory_movement.operation_type = 'purchase_in'` 的 `total_amount` 汇总。
2. `sales_amount`：`inventory_movement.operation_type = 'sales_out'` 的 `total_amount` 汇总。
3. `net_cash_flow`：`sales_amount - purchase_amount`。这不是利润，只代表采购支出和销售收入的现金流差额。
4. `purchase_count`：时间范围内 `operation_type = 'purchase_in'` 的库存流水条数。
5. `sales_count`：时间范围内 `operation_type = 'sales_out'` 的库存流水条数。
6. `movement_count`：时间范围内 `purchase_in` 和 `sales_out` 库存流水条数总和，即 `purchase_count + sales_count`。
7. 对外数量一律返回正数：`purchase_quantity = SUM(quantity_delta)` for `purchase_in`，`sales_quantity = SUM(-quantity_delta)` for `sales_out`。`inventory_movement.quantity_delta` 本身仍保持入库为正、出库为负。
8. `average_purchase_unit_cost`：同一商品历史采购金额 / 历史采购数量；采购数量只统计正数入库。该字段仅作为内部估值口径，BE-03 默认不对外输出。
9. `estimated_inventory_value`：库存金额估算。摘要级必须按商品分别计算后求和：`Σ(每个 product_uid 当前实时库存数量 * 该 product_uid 全历史采购加权平均单价)`；不得使用全局平均成本乘以总库存。单商品没有采购成本时，该商品估值按 `0` 计，并在响应中标记 `valuation_method = "weighted_average_purchase_cost"`。
10. 金额类响应字段统一保留 2 位小数，包括 `purchase_amount`、`sales_amount`、`net_cash_flow`、`estimated_inventory_value`、`top_products_by_sales.sales_amount`。实现使用 PostgreSQL `numeric` / Python `Decimal` 后再 `ROUND(..., 2)`，不得用二进制浮点直接拼响应。
11. `date_from/date_to` 只影响采购金额、销售金额、交易次数、流水次数和热销商品统计；库存数量、低库存列表、库存金额估算始终使用当前实时库存。
12. 库存金额估算使用全历史采购加权平均成本，不随查询时间范围截断。
13. 【跟踪决定，2026-07-31 PM 批准】采购/销售金额与交易次数（`purchase_amount/sales_amount/purchase_count/sales_count/top_products_by_sales`）按 `type = 'physical'` 全量统计，**不**过滤 `status = 'active'`；而库存、商品数、商品汇总、低库存按 active physical 统计。当前系统无商品停用 API，历史数据与实时库存在此口径下等价；若后续引入"停用商品"，必须由 PM 明确历史经营数据是否继续纳入摘要，再调整本口径。

### 2.3 库存

1. `current_stock_quantity`：当前店铺 active physical 商品的当前真实仓库/库位库存行数量汇总。
2. `product_count`：当前店铺 active physical 商品数；`knowledge`、`financial`、`human` 等非库存资源不得计入 Seller 商品。
3. `stock_location_count`：当前店铺 active physical 商品有库存记录的仓库/库位行数。`quantity = 0` 的真实库位行仍计数；没有任何库存行的 active physical 商品不增加 `stock_location_count`。
4. Seller 摘要默认只统计真实仓库/库位库存行，排除 `location_path = 'total'` 的汇总行，避免同时存在总计行和明细行时重复计数。
5. `low_stock_items`：所有 active physical 商品都参与判断；按商品聚合真实库位库存后，当前数量 `<= low_stock_threshold` 的商品汇总，默认阈值为 `5`，可通过查询参数传入。没有任何库存行的 active physical 商品按 `0` 库存处理，必须进入低库存判断。
6. MVP 假设同一 `product_uid` 只有一个业务单位。`low_stock_items.unit` 和 `product-summary.unit` 优先取 `resource.unit`；为空时取该商品最新库存流水的 `unit`；仍为空时返回 `null`。如果同商品多库位出现不同单位，本轮不做单位换算。

## 3. API 契约草案

### 3.1 经营摘要

`GET /seller/summary`

查询参数：

| 参数 | 必填 | 说明 |
|------|------|------|
| `date_from` | 否 | 开始日期，`YYYY-MM-DD` |
| `date_to` | 否 | 结束日期，`YYYY-MM-DD` |
| `low_stock_threshold` | 否 | 低库存阈值，默认 `5` |
| `top_n` | 否 | 热销商品数量，默认 `5`，最大 `20` |

成功响应：

```json
{
  "status": "ok",
  "date_from": "2026-07-01",
  "date_to": "2026-07-31",
  "sales_amount": 450.0,
  "purchase_amount": 300.0,
  "net_cash_flow": 150.0,
  "purchase_count": 3,
  "sales_count": 8,
  "movement_count": 11,
  "product_count": 4,
  "stock_location_count": 6,
  "current_stock_quantity": 32.0,
  "estimated_inventory_value": 256.0,
  "valuation_method": "weighted_average_purchase_cost",
  "low_stock_items": [
    {
      "product_uid": "phone_case_white",
      "quantity": 3.0,
      "unit": "件"
    }
  ],
  "top_products_by_sales": [
    {
      "product_uid": "phone_case_white",
      "sales_amount": 180.0,
      "sales_quantity": 12.0
    }
  ]
}
```

业务规则：

1. 必须使用 Bearer JWT。
2. 只能统计当前 JWT 所属店铺。
3. 响应不得出现 `id`、`organization_id`、`person_id`、`resource_id`、`warehouse_id`、`transaction_id`。
4. 日期格式错误返回 422。
5. `low_stock_threshold < 0` 返回 422。
6. `low_stock_threshold=0` 时，只有当前库存 `<= 0` 的 active 商品进入 `low_stock_items`。
7. `top_products_by_sales` 按 `sales_amount DESC, product_uid ASC` 排序，最多返回 `top_n` 个商品。
8. `top_n` 必须在 `1..20`。
9. 响应始终包含 `date_from`、`date_to` 两个键；未传对应参数时返回 `null`，不省略字段。

### 3.2 库存流水增强查询

增强现有 `GET /seller/inventory-movements`。

默认行为必须和 BE-02 已验收契约一致：不传新增查询参数时，响应仍然是库存流水数组，不包裹 `{status, items, pagination}`。这是 BE-02 回归红线。

查询参数：

| 参数 | 必填 | 说明 |
|------|------|------|
| `product_uid` | 否 | 商品业务 UID |
| `operation_type` | 否 | `purchase_in` 或 `sales_out` |
| `date_from` | 否 | 开始日期 |
| `date_to` | 否 | 结束日期 |
| `limit` | 否 | 默认不限制；传入时最大 `200` |
| `offset` | 否 | 默认 `0`；未传 `limit` 时忽略 |

成功响应：

```json
[
  {
    "movement_uid": "mv_xxxxxx",
    "operation_type": "sales_out",
    "product_uid": "phone_case_white",
    "warehouse_code": "main",
    "location_path": "A-01-03",
    "quantity_delta": -3.0,
    "new_quantity": 17.0,
    "unit": "件",
    "total_amount": 45.0,
    "counterparty_name": "淘宝买家",
    "created_at": "2026-07-31T10:20:30"
  }
]
```

业务规则：

1. `operation_type` 只能是 `purchase_in`、`sales_out`，其他值返回 422。
2. 如传入 `limit`，必须在 `1..200`。
3. `offset` 必须大于等于 `0`；未传 `limit` 时忽略 `offset`，不得因此改变默认 list 结果。
4. 不返回数据库数字主键。
5. 排序保持 `created_at DESC, movement_uid DESC` 或等价稳定倒序；同一时间内顺序必须稳定。
6. `product_uid` 在当前店铺不存在、不是 active 商品或不是 physical 商品时，按查询语义返回 `200 []`，不返回 404，也不得泄漏其他店铺是否存在同名商品。

### 3.3 商品经营汇总

新增 `GET /seller/product-summary`。

查询参数：

| 参数 | 必填 | 说明 |
|------|------|------|
| `product_uid` | 否 | 不传则返回当前店铺所有商品 |
| `date_from` | 否 | 统计开始日期 |
| `date_to` | 否 | 统计结束日期 |

成功响应：

```json
{
  "status": "ok",
  "items": [
    {
      "product_uid": "phone_case_white",
      "unit": "件",
      "current_quantity": 17.0,
      "purchase_quantity": 20.0,
      "sales_quantity": 3.0,
      "purchase_amount": 160.0,
      "sales_amount": 45.0,
      "movement_count": 2,
      "estimated_inventory_value": 136.0
    }
  ]
}
```

业务规则：

1. `purchase_quantity`、`sales_quantity`、`purchase_amount`、`sales_amount` 按时间范围统计，其中 `purchase_quantity`、`sales_quantity` 对外均为正数。
2. `current_quantity` 永远表示当前实时库存，不受 `date_from/date_to` 影响。
3. `estimated_inventory_value` 使用当前实时库存和历史加权平均采购成本估算。
4. 不返回数据库数字主键。
5. 不传 `product_uid` 时返回当前店铺所有 active physical 商品；没有流水的商品也要返回，采购/销售指标为 `0`。
6. `product_uid` 在当前店铺不存在、不是 active 商品或不是 physical 商品时，按查询语义返回 `200 {"status": "ok", "items": []}`，不返回 404，也不得泄漏其他店铺是否存在同名商品。

## 4. 数据库和实现设计

### 4.1 新增查询 helper

在 `src/db/database.py` 新增只读 helper：

```python
def get_seller_summary(
    organization_id: int,
    date_from: str | None = None,
    date_to: str | None = None,
    low_stock_threshold: float = 5,
    top_n: int = 5,

    ...

def query_inventory_movements(
    organization_id: int,
    product_uid: str | None = None,
    operation_type: str | None = None,
    date_from: str | None = None,
    date_to: str | None = None,
    limit: int | None = None,
    offset: int = 0,

    ...

def query_product_summary(
    organization_id: int,
    product_uid: str | None = None,
    date_from: str | None = None,
    date_to: str | None = None,
) -> dict:
    ...
```

实现要求：

1. 所有 SQL 必须带当前 JWT 上下文解析出的内部 `organization_id` 条件。
2. 查询 helper 只能返回业务字段；内部主键只用于 JOIN 和过滤。
3. SQL 使用参数化查询，不拼接用户输入。
4. 日期过滤统一复用内部私有 helper，避免每个查询重复实现。
5. 本轮不新增需要迁移的数据表，优先使用 `inventory_movement`、`resource_warehouse`、`resource`、`warehouse`、`transaction`。
6. 库存汇总 SQL 必须排除 `resource_warehouse.location_path = 'total'`，除非后续 PM 明确批准变更统计口径。
7. 不修改 `execute_purchase_in()`、`execute_sales_out()` 的事务边界、返回结构和异常语义；BE-03 只增加只读汇总能力。
8. 在 `SCHEMA_SQL` 中补充只读查询索引，不新增业务表：
   - `CREATE INDEX IF NOT EXISTS idx_im_org_created_at ON inventory_movement(organization_id, created_at DESC);`
   - `CREATE INDEX IF NOT EXISTS idx_im_org_op_created_at ON inventory_movement(organization_id, operation_type, created_at DESC);`

Router 要求：

3. 不直接依赖数据库数字主键做断言。
4. 测试环境使用 `agents/tdd/测试执行指南.md` 中的测试库配置。
5. 日期过滤测试只使用 API 产生的当前时间流水，用 Asia/Shanghai 的 today/tomorrow/yesterday 验证包含和排除，不允许直接 UPDATE `created_at`。
6. 三国 HTTP 回归作为验收命令执行，不写进 `test_seller_summary_api.py` 内部触发嵌套 pytest。

## 8. Review 红线

以下任一情况出现，BE-03 不允许合并：

1. `/seller/summary`、`/seller/product-summary` 或 `/seller/inventory-movements` 可匿名访问。
2. 查询结果混入其他店铺数据。
3. 响应体返回数据库数字主键。
4. 统计口径和本计划不一致，且没有 PM 批准的文档更新。
5. 日期过滤边界不明确或测试不可复现。
6. 为了实现摘要而破坏 BE-02 事务函数。
7. 三国 HTTP 回归失败且无法证明是既有问题。
8. 不传新增查询参数时，`/seller/inventory-movements` 默认响应不再是 BE-02 已验收的 list。
9. BE-03 为实现查询摘要改动 BE-02 入库/出库事务函数的提交、回滚、返回结构或 409 语义。
10. 摘要库存估值使用全局平均成本乘总库存，而不是按商品估值后求和。
11. 身份/内部主键查询参数被静默忽略，或能通过这些参数改变 JWT 店铺上下文。
12. 对外汇总数量把 `sales_out` 的负数 `quantity_delta` 直接暴露为负销售数量。
13. `current_stock_quantity` 统计 inactive 商品残留库存。
14. Seller 摘要或商品汇总把非 physical 资源当作库存商品统计。
