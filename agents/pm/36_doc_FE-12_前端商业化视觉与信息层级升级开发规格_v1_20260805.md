# FE-12 开发规格：前端商业化视觉与信息层级升级

> 日期：2026-08-05
> 角色：PM / 产品负责人
> 状态：待下发开发团队
> 背景：现有 `frontend/` 已完成功能闭环，但整体视觉和信息层级仍偏“能用的原型”，不足以支撑比赛展示和商业化观感。本规格只调整前端产品设计与视觉结构，不新增后端业务能力。

---

## 1. 目标

把当前前端从“功能面板”升级为“产品级经营工作台”。

用户打开系统后，第一眼应当清楚看到：

1. 我是谁。
2. 我在哪个组织/业务空间里。
3. 这个空间能做什么。
4. 我现在最该做什么。

本阶段的核心不是堆功能，而是补齐：

- 商业系统感
- 多空间上下文感
- 操作密度
- 展示层级
- 录屏可读性

---

## 2. 现状判断

当前前端已具备这些功能：

- `AppHeader`、`SidebarNav`、`WorkbenchView`、`ProductsView`、`StockView`、`MovementsView`、`SummaryView`、`ChatView`、`GenericSpaceView`
- 登录、组织切换、Seller 工作台、通用空间观察、AI 查询、空间治理入口

但视觉问题很明显：

- Header 仍像原生表单拼装，缺少上下文卡片感。
- Sidebar 是纯文本按钮列表，像调试导航，不像业务工作区。
- Workbench 仍是简单的 KPI + 表格 + 侧栏拼接，缺少主次层级。
- Summary 页信息密度不足，四个卡片没有形成经营分析面板。
- GenericSpaceView 更像日志展开页，不像空间观察台。
- ChatView 是重复卡片，AI 页显得薄。

结论：功能已通，产品感不足。

---

## 3. 设计原则

1. **上下文优先**  
   Header 只做身份、空间、角色、切换、治理，不做第二个 AI 入口。

2. **工作台优先**  
   Seller 空间要像经营驾驶舱，不像后台列表页。

3. **密度高但不拥挤**  
   页面要有信息层级，不要把所有内容放成同权重卡片。

4. **统一壳体，不同内容**  
   Seller 和非 Seller 共用同一前端壳体，但主视觉和内容结构要区分。

5. **不做营销页**  
   不引入大横幅、空洞口号、装饰性插画、占据首屏的大块空白。

6. **不暴露 DB 数字 ID**  
   所有列表、卡片、标签、表格、提示都只展示业务字段。

7. **颜色克制，状态明确**  
   主色使用深色中性 + 业务强调色，不要做单一紫色/蓝色渐变堆叠。

8. **输入位置唯一**  
   AI 对话输入只允许出现在独立 `ChatView`。Workbench 右侧可以展示 AI 摘要，但不能出现可输入聊天框。

## 4. 视觉系统

### 4.1 色彩

建议采用“深色导航 + 浅色内容区 + 强调色”的组合：

- 背景：浅灰白
- Header：白底或极浅灰底
- Sidebar：深蓝灰/深石板色
- 主强调色：青绿/蓝绿
- 警告色：橙黄
- 危险色：红色

约束：

- 不要用纯装饰性渐变做主视觉。
- 不要让页面只剩单一蓝色调。
- 状态颜色必须服务于业务语义，而不是装饰。
- Sidebar 建议使用 `#1E293B` 或同级深蓝灰；主内容区背景建议使用 `#F8FAFC`。
- 主强调色只用于按钮、标签和激活态，不要大面积铺满背景。
- 禁止红配绿制造强冲突：低库存用橙色 `#F59E0B`，危险/停用用红色 `#EF4444`，正常/完成用绿色 `#10B981`。

### 4.2 字体与层级

- 页面主标题：24-28px，700+。
- 区块标题：16-18px，700。
- 正文：13-14px。
- 辅助信息：12px。

规则：

- 标题必须区分主次。
- 数字型 KPI 要比说明文字大一到两级。
- 不允许整个页面所有字重都一样。
- 标题 `line-height: 1.3`。
- 正文 `line-height: 1.6`。
- 数字型 KPI 必须右对齐，便于快速比较。
- 中文描述、表单标签、列表说明左对齐。

### 4.3 圆角、边框、阴影

- 卡片圆角：8px 左右。
- 表单圆角：6px-8px。
- Border：细线分隔，不靠重阴影撑层级。
- 阴影仅用于浮层、下拉、弹窗、抽屉。

### 4.4 图标和按钮

- 按钮优先使用图标 + 文案。
- 常用操作使用明确图标：刷新、切换、入库、出库、搜索、复制、退出。
- 禁止把圆角文字块当成唯一状态表达，能用图标或 chip 的优先用图标/chip。

## 5. 全局布局

目标结构：

```text
┌─────────────────────────────────────────────────────────────┐
│ AppHeader                                                   │
│ [Logo] 当前用户 | 当前组织 | 空间切换 | 治理入口 | 退出      │
├─────────┬───────────────────────────────────────────────────┤
│ Sidebar │ Main View                                          │
│ 导航菜单 │ 业务视图 / 空间观察 / 治理页面                    │
└─────────┴───────────────────────────────────────────────────┘
```

### 5.1 AppHeader

Header 的任务是“上下文层”，不是“操作层”。

必须显示：

- 当前用户姓名 + `puid`
- 当前组织名 + `ouid`
- 当前组织类型
- 当前角色
- 当前账号可切换的组织列表

建议形式：

- 左侧：Logo + 产品名
- 中间：当前用户/当前空间信息卡
- 右侧：空间切换、空间治理、退出登录

设计要求：

- 组织切换应像一个清晰的下拉选择器或按钮组，不要只是原生 select。
- 当前空间信息建议以“组织卡片”呈现：组织名、类型 chip、角色 chip。
- Header 不应显示完整 AI 入口。
- Header 不应重复 Sidebar 的业务导航。
- 480px 窄屏下 Header 不能折成多行按钮。组织信息卡片缩略为“组织名（截断）”，`puid`、角色、类型、`ouid` 收进下拉详情。
- 窄屏下 Header 仍要保证空间切换、空间菜单、退出入口可达，且不横向溢出。

### 5.2 Sidebar

Sidebar 是“当前空间内的工作区导航”。

Seller 空间导航：

- 工作台
- 商品
- 库存
- 库存流水
- 经营摘要
- Seller AI

非 Seller 空间导航：

- 空间总览
- 资源
- 人员
- 时间线
- 多维观察

设计要求：

- 导航项应有图标或明确状态标识。
- 当前项高亮要明显。
- 导航项之间要分组，避免纯文本列表感。
- Seller 空间和非 Seller 空间的侧边栏视觉可以一致，但信息优先级必须不同。

### 5.3 Main View

主区不允许像“几个同级卡片拼接”。

Seller 空间主区优先采用：

1. 顶部经营摘要条
2. 中部核心业务区
3. 右侧预警 / AI 摘要区
4. 底部最近流水或补充信息区

非 Seller 空间主区优先采用：

1. 概览条
2. 资源/人员主面板
3. 时间线
4. 多维流向

## 6. 页面级设计

### 6.1 登录页

登录页保持克制，不做营销页。

要求：

- 中央登录表单清晰。
- 左右可选轻量产品说明或场景摘要，但不得喧宾夺主。
- 默认账号提示应是业务账号，不要再强调旧的多账号格式。
- 错误态、加载态、空态要明确。

### 6.2 Seller 工作台

这是最重要的展示页，必须做成“经营驾驶舱”。

建议布局：

- 顶部：标题 + 状态说明 + 入库/出库主按钮
- 顶部标题下增加“今日快照”行：
  - 示例：`截至 2026-08-05 14:30 · 最近更新：2 分钟前`
  - 时间可先使用前端当前时间，不要求后端新增字段。
- 第一层：5 个 KPI 卡片
  - 销售收入
  - 采购支出
  - 净现金流
  - 库存估值
  - 低库存数量
- 第二层左侧：库存明细主表
- 第二层右侧：低库存预警 + AI 摘要卡片
- 第三层：最近流水或关键动作摘要

要求：

- KPI 卡片要有视觉差异，不要做成一排完全同质的方块。
- KPI 差异不要靠花哨背景，靠数字强调、辅助图标和微趋势：
  - 销售收入右上角可显示 `↑12%` 这类前端占位趋势。
  - 低库存数字使用橙色。
  - 净现金流为负时数字使用红色。
  - 卡片背景保持沉稳，避免做成炒股软件首页。
- 低库存区域要具备风险感，不只是列表。
- Workbench 右侧 AI 只做“上下文快照摘要”，不可输入对话。
- AI 摘要卡片可展示：低库存摘要、经营异常提示、建议查看的问题。
- 深度多轮对话只进入独立 `ChatView`。
- 入库/出库按钮要做成主操作，不要埋在普通按钮里。

### 6.3 商品页

商品页应像“主数据管理页”，不是普通表格页。

建议结构：

- 页面标题 + 简短说明
- 顶部筛选条：状态、搜索、单位
- 主表格：商品编码、单位、状态、库存总数、库位数
- 右侧或弹窗：新建/编辑/停用

要求：

- 视觉上要清楚区分 active / inactive。
- 新建与停用动作要有明确危险提示。
- 不要把商品页做成冷冰冰的 CRUD 表单。

### 6.4 库存页

库存页重点是“看库存位置”。

建议结构：

- 顶部过滤条：商品、仓库、状态
- 主表：商品、仓库、库位、数量、单位、风险标记
- 低库存 tag 视觉可见

要求：

- 让用户一眼看出哪个库位快没货。
- 行 hover、风险高亮、tag 状态必须统一。

### 6.5 库存流水页

流水页不应像简单日志。

建议结构：

- 顶部筛选：操作类型、日期范围、limit
- 主体：按时间倒序的流水表或时间轴
- 对不同操作类型使用不同语义色

要求：

- 出库、入库、调整等类型要有明确视觉区分。
- 日期和类型筛选要在同一层级。

### 6.6 经营摘要页

摘要页应是“经营分析面板”。

建议结构：

- 顶部：4 个关键指标卡
- 中部：低库存商品 + 热销商品
- 底部：库存估值 / 现金流补充视图

要求：

- 低库存和热销商品不要只是列表，要有可扫读性。
- 数字要大，标签要小。
- 如果没有图表库，就用条形长度或强调色块模拟趋势感，但不要空。

### 6.7 Seller AI 页

AI 页应比现在更像一个“工具页”，而不是复用聊天框。

建议结构：

- 顶部：标题 + 只读提示
- 中部：聊天记录
- 右侧或顶部：快捷问题 chip
- 底部：输入框 + 发送按钮
- AI 回复底部增加轻量来源提示，例如：`引用 3 条库存记录`。
- MVP 不要求点击跳转来源，但要体现“回答来自系统数据，不是凭空生成”。

快捷问题建议：

- 库存最低的商品是什么？
- 这个月卖了多少钱？
- 采购支出是多少？
- 低库存有哪些？

要求：

- AI 页必须强调“只读查询”。
- 不要和 Header 重复。
- 返回结果要能被快速扫到，不只是长文本气泡。
- 独立 `ChatView` 是唯一可输入对话的 AI 入口。

### 6.8 通用空间观察页

非 Seller 空间要像“观察台”，不是“待接入页”。

建议结构：

- 顶部概览条：空间名、类型、角色、资源数、人员数、交易数、最近事件数
- 中部：4 个“观察雷达卡片”
  - Resources：资源总数 + 最近一条资源变化
  - Persons：人员总数 + 最近一条人员/参与方变化
  - Finance：资金总额/交易数 + 最近一条交易
  - Knowledge：知识资源数 + 最近一条事件信息
- 下方左侧：资源与人员
- 下方右侧：时间线与多维流向
- 底部：明细列表

要求：

- `overview`、`resources`、`persons`、`timeline`、`flows` 五块要有视觉锚点。
- 资源分组必须清晰。
- 时间线要像复盘，而不是日志 dump。
- “多维流向”不得做复杂关系图谱、力导向图或拓扑图。本轮只做 4 个雷达卡片 + 列表分组。
- 物理资源、知识资源、人力资源、资金流要分层展示。
- 人员列表使用头像缩写占位，例如圆形背景 + 姓名首字。
- 资源列表使用小图标或标签强化类型，不要只有纯文字。

## 7. 交互与状态

1. **组织切换**
   - 切换成功后刷新上下文、重置主视图、回到目标空间默认页。
   - 切换失败保留原状态并提示错误。

2. **加载状态**
   - 每个页面必须有明确 loading。
   - 不能出现长时间白屏。

3. **空状态**
   - 空态必须是有信息的空态，不是“敬请期待”。
   - 只读页面可以空，但要说明缺少什么数据。
   - 必须按三类模板实现：
     - 引导型：数据为 0 时，说明下一步并给主按钮。例如商品为 0：`添加第一个商品，开始管理库存` + `新增商品`。
     - 过滤型：搜索/筛选无结果时，复述筛选条件并提示调整。例如：`没有匹配“xx”的商品，试试调整筛选条件`。
     - 只读型：无流水/无事件时，说明数据来源。例如：`当前暂无流水，入库、出库或交易后将在此显示`。
   - 禁止纯灰底 + 一行居中小字。

4. **错误状态**
   - 401 直接回登录。
   - 普通错误显示后端返回信息或友好文案。

5. **响应式**
   - 1440：完整展示。
   - 1280：保持主体完整，不横向溢出。
   - 480：侧边栏折叠或转为可收起菜单，主操作仍可用。
   - 小于 768px：Header 中间组织卡片只显示组织名，其他上下文信息进入下拉详情；所有 Header 操作按钮必须在一行内或收进菜单。

6. **容器对齐**
   - Main View 里的卡片必须左右对齐。
   - 同一行卡片高度应使用 grid/flex 的 `align-stretch` 保持一致。
   - 禁止出现左列很长、右列很短且底部参差的核心布局。

## 8. 设计边界

本轮不做：

- 不改后端业务 API。
- 不新增新的业务空间模型。
- 不加营销首页。
- 不把 Header 再改回第二个 AI 入口。
- 不引入复杂动画和重装饰。
- 不做大范围路由重构。

本轮只做：

- 前端壳体升级
- 视觉层级升级
- 组件重排
- 空间上下文强化
- Seller / 非 Seller 双风格统一

## 10. 验收标准

### 10.1 视觉验收

- 1440、1280、480 三个宽度下不溢出。
- Header 能一眼看到用户、组织、角色、切换入口。
- 480px 下 Header 不折成难看的多行按钮，组织信息自动缩略。
- Sidebar 明显是业务导航，不是纯文本菜单。
- Workbench 看起来像经营驾驶舱，不像基础表格页。
- Workbench 右侧 AI 摘要不可输入；独立 `ChatView` 才能输入。
- KPI 数字右对齐，正负/低库存状态颜色正确。
- 三类空状态（引导型、过滤型、只读型）均有测试或截图覆盖。
- GenericSpace 看起来像观察台，不像日志页。
- GenericSpace 采用 4 个观察雷达卡片，不做复杂关系图。
- AI 页看起来像工具页，不像重复面板。

### 10.2 功能验收

- 组织切换后主区和侧栏同步刷新。
- Seller 空间不调用非 Seller 页面。
- 非 Seller 空间不调用 `/seller/*`。
- Header 不出现 AI button。
- Workbench 不出现 `chat-input`。
- 不暴露 DB 数字 ID。

### 10.3 自动化验收

建议保留并补充以下检查：

```bash
cd frontend && npm run test
cd frontend && npm run build
rg -n 'header-ai|navigate-ai|问 AI|AI button' frontend/src
rg -n 'person_id|organization_id|resource_id|warehouse_id|transaction_id' frontend/src
```

## 11. PM 结论

当前前端功能已够，但产品感不够。  
本轮应按“产品化视觉升级”执行，不再只修补局部样式。

开发团队的交付目标不是“能点”，而是“像一个真正可展示、可演示、可交付的商业系统”。
