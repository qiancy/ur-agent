# BE-02 开发计划：卖家库存事务原子性

> 角色：开发团队负责人
> 前置状态：BE-01 已提交，身份上下文严格收口为 `puid/ouid`；不保留旧身份键适配；业务端不得接收或返回数据库数字主键。
> 执行原则：先 TDD 红灯，再后端实现，再编译和回归验证。不得跳过红灯测试直接实现。

## 1. 目标和非目标

### 1.1 目标

BE-02 只解决淘宝卖家 MVP 的库存事务一致性：

1. 提供 `purchase_in` 买入入库能力：库存增加，同时记录采购交易和库存流水。
2. 提供 `sales_out` 卖出出库能力：库存扣减，同时记录销售交易和库存流水。
3. 新增 `inventory_movement` 库存流水，能追溯操作者、店铺、商品、仓库、库位、数量变化、金额、交易和时间。
4. 入库/出库必须在一个数据库事务内完成：库存变动、交易记录、库存流水同生同死。
5. 出库必须在同一事务内锁定库存行并校验库存充足，禁止负库存。
6. Seller API 只暴露业务字段，不把 `resource_id`、`warehouse_id`、`transaction.id` 当业务字段传给前端或测试脚本。
7. BE-01 安全隔离继续成立：ecommerce 店铺所有 Seller 操作必须使用 JWT 上下文，店铺之间不可读写对方库存。

### 1.2 非目标

本轮不做：

1. 淘宝开放平台订单同步。
2. 多规格 SKU、条码、批次、保质期。
3. 退货入库、盘点、损耗、报废。
4. 前端工作台页面。
5. AI 自然语言入库/出库工具。
6. 财务总账重构或复杂应收应付。
7. 旧表字段迁移或旧身份键适配。字段变更通过重建表解决。

## 2. API 契约草案

### 2.1 通用约束

1. 所有 `/seller/*` 接口必须使用 Bearer JWT。
2. 组织和操作者来自 JWT 解析结果：`ouid`、`puid`、`organization_id`、`person_id` 只在服务端上下文中使用。
3. 请求体不得包含 `organization_id`、`person_id`、`resource_id`、`warehouse_id`。
4. 响应体不得返回 `id`、`organization_id`、`person_id`、`resource_id`、`warehouse_id`、`transaction_id`。
5. 可返回的业务字段：`product_uid`、`product_name`、`warehouse_code`、`location_path`、`quantity`、`unit`、`total_amount`、`counterparty_name`、`movement_uid`、`operation_type`、`created_at`、`status`。

### 2.2 买入入库

`POST /seller/purchase-in`

请求：

```json
{
  "product_uid": "phone_case_white",
  "warehouse_code": "main",
  "location_path": "A-01-03",
  "quantity": 20,
  "unit": "件",
  "total_amount": 160,
  "counterparty_name": "义乌供应商"
}
```

成功响应：

```json
{
  "status": "ok",
  "operation_type": "purchase_in",
  "product_uid": "phone_case_white",
  "warehouse_code": "main",
  "location_path": "A-01-03",
  "quantity_delta": 20,
  "new_quantity": 20,
  "unit": "件",
  "total_amount": 160,
  "counterparty_name": "义乌供应商",
  "movement_uid": "mv_20260731_xxxxxx"
}
```

业务规则：

1. `quantity` 必须大于 0。
2. `total_amount` 必须大于等于 0。
3. 如果目标库位不存在，可在事务内创建库存行并从 0 加起。
4. 采购交易方向为支出，摘要层按 `category = purchase_in` 统计采购支出。

### 2.3 卖出出库

`POST /seller/sales-out`

请求：

```json
{
  "product_uid": "phone_case_white",
  "warehouse_code": "main",
  "location_path": "A-01-03",
  "quantity": 3,
  "unit": "件",
  "total_amount": 45,
  "counterparty_name": "淘宝买家"
}
```

成功响应：

```json
{
  "status": "ok",
  "operation_type": "sales_out",
  "product_uid": "phone_case_white",
  "warehouse_code": "main",
  "location_path": "A-01-03",
  "quantity_delta": -3,
  "new_quantity": 17,
  "unit": "件",
  "total_amount": 45,
  "counterparty_name": "淘宝买家",
  "movement_uid": "mv_20260731_yyyyyy"
}
```

业务规则：

1. `quantity` 必须大于 0。
2. `total_amount` 必须大于等于 0。
3. 目标库位不存在时返回 404 或 409，不能自动创建负库存行。
4. 库存不足时返回 409，库存、交易、流水全部不变。
5. 销售交易方向为收入，摘要层按 `category = sales_out` 统计销售收入。

### 2.4 库存和流水查询

BE-02 可按测试需要补充最小查询接口：

| 方法 | 路径 | 用途 | 业务字段 |
|------|------|------|----------|
| `GET` | `/seller/stock?product_uid=...` | 查询当前店铺库存 | `product_uid`, `warehouse_code`, `location_path`, `quantity`, `unit` |
| `GET` | `/seller/inventory-movements?product_uid=...` | 查询库存流水 | `movement_uid`, `operation_type`, `product_uid`, `warehouse_code`, `location_path`, `quantity_delta`, `new_quantity`, `counterparty_name`, `created_at` |

查询响应同样禁止返回数据库数字主键。

## 3. 数据库和事务设计

### 3.1 表结构建议

字段变更按当前项目规则处理：修改 `SCHEMA_SQL` 后重建表，不写迁移适配。

`resource` 建议补充商品业务 UID：

```sql
product_uid VARCHAR(100),
CONSTRAINT uq_resource_org_product_uid UNIQUE (organization_id, product_uid)
```

如果本轮暂不改 `resource` 表，可短期用 `resource.name` 承担 `product_uid` 查找，但 PM 建议 BE-02 直接显式落库 `product_uid`，避免商品展示名和业务 UID 绑定。

`resource_warehouse` 建议补充内部仓库外键：

```sql
warehouse_id INTEGER NOT NULL REFERENCES warehouse(id) ON DELETE CASCADE,
UNIQUE(resource_id, warehouse_id, location_path)
```

API 仍只接收 `warehouse_code`，后端在当前 `organization_id` 内解析为内部 `warehouse.id`。

新增 `inventory_movement`：

```sql
CREATE TABLE inventory_movement (
    id                  SERIAL PRIMARY KEY,
    movement_uid        VARCHAR(100) UNIQUE NOT NULL,
    organization_id     INTEGER NOT NULL REFERENCES organization(id) ON DELETE CASCADE,
    operator_person_id  INTEGER NOT NULL REFERENCES person(id),
    resource_id         INTEGER NOT NULL REFERENCES resource(id),
    warehouse_id        INTEGER REFERENCES warehouse(id),
    resource_warehouse_id INTEGER NOT NULL REFERENCES resource_warehouse(id),
    transaction_id      INTEGER NOT NULL REFERENCES transaction(id) ON DELETE CASCADE,
    operation_type      VARCHAR(50) NOT NULL,
    quantity_delta      DECIMAL(15,2) NOT NULL,
    quantity_after      DECIMAL(15,2) NOT NULL,
    unit                VARCHAR(50),
    total_amount        DECIMAL(15,2) NOT NULL DEFAULT 0,
    counterparty_name   VARCHAR(255),
    created_at          TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CHECK (operation_type IN ('purchase_in', 'sales_out'))
);
```

索引：

```sql
CREATE INDEX idx_inventory_movement_org ON inventory_movement(organization_id);
CREATE INDEX idx_inventory_movement_resource ON inventory_movement(resource_id);
CREATE INDEX idx_inventory_movement_warehouse ON inventory_movement(warehouse_id);
CREATE INDEX idx_inventory_movement_transaction ON inventory_movement(transaction_id);
CREATE INDEX idx_inventory_movement_created_at ON inventory_movement(created_at);
```

### 3.2 原子函数

在 `src/db/database.py` 新增两个事务函数：

```python
def execute_purchase_in(
    organization_id: int,
    operator_person_id: int,
    product_uid: str,
    warehouse_code: str,
    location_path: str,
    quantity: float,
    unit: str | None,
    total_amount: float,
    counterparty_name: str | None,
) -> dict:
    ...

def execute_sales_out(
    organization_id: int,
    operator_person_id: int,
    product_uid: str,
    warehouse_code: str,
    location_path: str,
    quantity: float,
    unit: str | None,
    total_amount: float,
    counterparty_name: str | None,
) -> dict:
    ...
```

红线：

1. 这两个函数自己打开一个数据库连接，自己控制 `commit/rollback`。
2. 函数内部不得调用现有 `_execute()`、`create_transaction()`、`create_resource_warehouse()` 这类会自行提交的 helper。
3. 需要复用逻辑时，只能拆成接收 `cur` 的内部私有 helper。
4. `commit()` 只能出现在库存更新、交易插入、流水插入全部成功之后。
5. 任一 SQL 或业务校验失败，必须 `rollback()` 后抛出业务异常，由 router 映射成 400/404/409/403。

### 3.3 purchase_in 事务顺序

1. 校验 `quantity > 0`、`total_amount >= 0`。
2. 在当前 `organization_id` 内解析 `product_uid -> resource.id`。
3. 在当前 `organization_id` 内解析 `warehouse_code -> warehouse.id`。
4. 取目标库存行：
   - 先 `INSERT ... ON CONFLICT DO NOTHING` 创建 0 库存行。
   - 再 `SELECT ... FOR UPDATE` 锁定 `(resource_id, warehouse_id, location_path)`。
5. `UPDATE resource_warehouse SET quantity = quantity + %s RETURNING quantity`。
6. 插入 `transaction`，`category = 'purchase_in'`，`amount = total_amount`。
7. 插入 `inventory_movement`，`quantity_delta = +quantity`，`quantity_after = new_quantity`。
8. `commit()`。
9. 返回 DTO 映射，不返回内部主键。

### 3.4 sales_out 事务顺序

1. 校验 `quantity > 0`、`total_amount >= 0`。
2. 在当前 `organization_id` 内解析 `product_uid -> resource.id`。
3. 在当前 `organization_id` 内解析 `warehouse_code -> warehouse.id`。
4. `SELECT ... FOR UPDATE` 锁定目标库存行。
5. 如果库存行不存在，返回 404 或 409，`rollback()`。
6. 如果 `current_quantity < requested_quantity`，返回 409，`rollback()`。
7. `UPDATE resource_warehouse SET quantity = quantity - %s RETURNING quantity`。
8. 插入 `transaction`，`category = 'sales_out'`，`amount = total_amount`。
9. 插入 `inventory_movement`，`quantity_delta = -quantity`，`quantity_after = new_quantity`。
10. `commit()`。
11. 返回 DTO 映射，不返回内部主键。

## 4. TDD 测试计划

BE-02 使用独立测试文件 `agents/tdd/test_seller_inventory_transaction_api.py`。执行顺序必须是：先提交失败测试，再实现后端。

保留 `agents/tdd/test_seller_inventory_api.py` 作为 BE-01 回归文件，不在其中追加 BE-02 事务用例。原因是 BE-01 覆盖旧的资源仓库隔离接口，仍会出现内部资源主键测试上下文；BE-02 必须单独验证 Seller API 不接收、不返回内部数据库主键。

最低 8 个 BE-02 测试：

| # | 测试名 | 覆盖点 |
|---|--------|--------|
| 1 | `test_purchase_in_increases_stock` | 买入入库后指定商品、仓库、库位库存增加 |
| 2 | `test_purchase_in_records_transaction_and_movement` | 同一次入库产生采购交易和库存流水 |
| 3 | `test_sales_out_decreases_stock` | 卖出出库后库存扣减，返回 `new_quantity` |
| 4 | `test_sales_out_rejects_insufficient_stock` | 库存不足返回 409，库存不变 |
| 5 | `test_other_shop_cannot_affect_shop_a_stock` | 店铺 B 不能改变店铺 A 的 `product_uid` 和库位库存 |
| 6 | `test_failed_sales_out_creates_no_transaction_or_movement` | 失败出库不产生交易和库存流水 |
| 7 | `test_inventory_movement_is_traceable_without_db_ids` | 流水可查，含业务字段，不含内部数字主键 |
| 8 | `test_seller_api_response_does_not_leak_db_ids` | 入库、出库、库存、流水响应均不含内部主键字段 |
| 9 | `test_purchase_in_rolls_back_when_movement_insert_fails` | 中途失败时库存和交易一起回滚；如 HTTP 难以稳定触发，可补 DB helper 级测试，不增加测试专用接口 |
| 10 | `test_three_kingdoms_http_regression` | 火烧新野 HTTP 回归不受 Seller 事务影响 |

测试数据规则：

1. 每次测试创建唯一 ecommerce 店铺 `ouid` 和卖家账号。
2. 商品使用业务字段 `product_uid`，不要在测试断言中依赖 `resource_id`。
3. 仓库使用 `warehouse_code`，库位使用 `location_path`，不要在测试断言中依赖 `warehouse_id`。
4. 查询交易和流水时只断言业务字段、金额、数量、方向和时间，不断言数据库主键。
5. 任何失败请求都要先记录库存、交易数、流水数，失败后再次查询确认完全不变。

## 7. PM Review Checklist

PM review 时逐项确认：

1. TDD 是否先红灯，且红灯原因和 BE-02 缺口一致。
2. `/seller/purchase-in` 是否只接收业务字段。
3. `/seller/sales-out` 是否只接收业务字段。
4. Seller 响应是否没有内部数据库数字主键。

6. 入库是否在同一事务内完成库存增加、交易插入、流水插入。
7. 出库是否使用行锁并在锁内校验库存充足。
8. 库存不足是否返回 409，且库存、交易、流水全部不变。
9. 事务函数内部是否没有调用会自行 `commit()` 的旧 helper。
10. `commit()` 是否只在全部操作成功后执行。
11. 任一异常路径是否执行 `rollback()`。
12. 店铺 B 是否无法操作店铺 A 的商品、仓库、库存和流水。
13. 所有 SQL 是否参数化。
14. 字段变更是否只通过重建表处理，没有字段迁移或旧协议适配层。
15. BE-01 的 8 个隔离测试是否仍然通过。
16. 火烧新野 HTTP 回归是否仍然通过。
17. `compileall` 和 `git diff --check` 是否通过。
