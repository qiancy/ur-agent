# BE-05 开发计划：卖家经营工作台前端重构

> 日期：2026-08-02  
> 角色：PM / 产品负责人  
> 状态：下达给前端开发团队，先做静态 demo 评审，再进入实现  
> 背景：当前 Gradio 前端功能能跑，但界面不具备付费产品质感。BE-05 目标不是继续修补旧 Tabs，而是重构卖家经营工作台的信息架构、视觉层级和核心操作闭环。

## 1. PM 结论

不需要安装前端 skill。当前问题可以通过明确产品目标、交互结构、视觉规范和验收标准解决。

BE-05 必须先产出 3 个静态 HTML demo 供 PM/用户选择风格。风格选定后，再做代码实现。未通过 demo 评审前，不允许直接改 `src/frontend.py` 大量代码。

## 2. 目标用户和购买理由

目标用户：中小淘宝/电商卖家，尤其是 1-10 人团队，库存、进货、出货和经营查询仍依赖 Excel、聊天记录或脑内记忆。

他们愿意付费的理由：

1. 一眼知道今天经营状况：销售收入、采购支出、库存金额、低库存风险。
2. 快速处理日常动作：入库、出库、查库存、查流水，不需要理解底层资源模型。
3. 能用自然语言问经营问题：库存还剩多少、哪些商品低库存、今天卖了多少钱、采购花了多少。
4. 数据安全：登录后只看当前店铺，前端、API、AI 均不暴露数据库数字 ID。

## 3. 范围

### 3.1 本轮必须做

1. 生成 3 个可直接打开的 HTML 静态 demo：
   - `docs/frontend-demos/be05-style-a-ops.html`
   - `docs/frontend-demos/be05-style-b-command.html`
   - `docs/frontend-demos/be05-style-c-owner.html`
2. demo 必须覆盖卖家核心页面：
   - 库存概览
   - 库存流水
   - 经营摘要
   - 低库存
   - Seller AI 查询
   - 入库/出库人工入口
3. demo 不得展示 `id`、`*_id`、数据库主键、旧 `pid/oid`。
4. demo 需要使用真实业务字段：
   - `product_uid`
   - `warehouse_code`
   - `location_path`
   - `quantity`
   - `quantity_delta`
   - `new_quantity`
   - `movement_uid`
   - `operation_type`
   - `sales_amount`
   - `purchase_amount`
   - `net_cash_flow`
5. 选定风格后，前端实现优先服务 ecommerce Seller 工作台。

### 3.2 本轮不做

1. 不重构后端 API。
2. 不引入 AI 写入库存。
3. 不做订单同步、物流同步、退款退货。
4. 不做复杂权限后台。
5. 不把真实密钥写入前端或文档。

## 4. 推荐技术路线

### 4.1 短期比赛交付

优先继续使用 Gradio，但要把页面结构重构为“工作台”，而不是直接堆 Tabs。

原因：

1. 后端和运行方式已稳定。
2. 比赛交付时间紧，React/Vite 会引入新的构建、部署和认证接线风险。
3. Gradio 可以通过 `Blocks + HTML/CSS + Dataframe + Group` 做出足够专业的 MVP 工作台。

### 4.2 中期产品化

比赛后迁移到 React/Vite 或 Next.js 前端。原因是 Gradio 在复杂表格、筛选、状态管理、响应式布局、视觉精度上上限有限。

## 5. 三个 demo 风格定义

### A. Ops Desk：专业后台型

定位：面向每天处理库存和流水的运营人员。

特点：

1. 左侧导航，顶部经营指标。
2. 中间主表格展示库存。
3. 右侧固定 AI 助手和低库存清单。
4. 风格克制、密度高、适合长期使用。

适合：最像可售卖 SaaS，建议默认优先。

### B. Command Board：异常优先型

定位：面向老板/店主，看风险和结果。

特点：

1. 首屏突出低库存、现金流、今日动作。
2. 把流水、补货建议、热销商品做成决策面板。
3. AI 区更像经营顾问。

适合：比赛展示冲击力强，但长期录入效率略低。

### C. Owner Console：店主日常型

定位：面向非专业仓库人员，手机/平板也能看。

特点：

1. 大按钮、卡片式库存和流水。
2. 入口直接：入库、出库、查库存、问 AI。
3. 信息少但路径短。

适合：小店老板上手快，但数据密度最低。

## 6. PM 推荐

PM 推荐先选 **A. Ops Desk** 作为比赛交付主风格，并吸收 B 的“低库存风险”和 C 的“快速入库/出库入口”。

最终实现应是：

1. 左侧：库存、流水、经营摘要、AI。
2. 顶部：销售收入、采购支出、净现金流、库存估值、低库存数。
3. 主区域：库存表格 + 筛选。
4. 右侧：AI 查询 + 低库存列表。
5. 页面不出现教学文案，不出现数据库数字 ID。

## 7. 前端实现任务拆分

### FE-01：选型和静态设计

负责人：前端负责人  
产出：3 个 HTML demo  
验收：PM 选择 1 个主风格，或明确混合方案。

### FE-02：Gradio 工作台结构重构

负责人：前端负责人  
改动文件：`src/frontend.py`  
要求：

1. 去掉当前卖家区域分散 Tabs 的体验。
2. 增加单屏工作台：指标区、库存区、流水区、AI 区。
3. 非 ecommerce 组织不显示 Seller 工作台。
4. Seller API 请求只使用 Bearer token。

### FE-03：数据呈现组件

负责人：前端负责人  
要求：

1. 库存使用表格展示，支持商品、仓库、库位、数量。
2. 流水支持操作类型、日期范围、条数。
3. 摘要指标用紧凑卡片展示。
4. 低库存必须首屏可见。

### FE-04：人工操作入口

负责人：前端负责人 + 后端负责人  
要求：

1. 提供入库表单。
2. 提供出库表单。
3. 操作成功后自动刷新库存、流水、摘要。
4. 表单只接受业务字段：`product_uid`、`warehouse_code`、`location_path`、`quantity`、`unit`、`total_amount`、`counterparty_name`。

### FE-05：AI 查询闭环

负责人：AI/前端负责人  
要求：

1. AI 固定在 Seller 工作台侧栏或下方区域。
2. 提供自然语言查询输入。
3. 快捷问题不得触发写入。
4. 回答不得出现 DB 数字 ID。

## 8. 验收标准

### 8.1 视觉验收

1. 首屏像一个可售卖的经营软件，不是开发调试界面。
2. 800px、1280px、1440px 宽度下不出现文字重叠。
3. 表格、卡片、按钮、输入框间距一致。
4. 页面主色不单调，不使用大面积紫蓝渐变。
5. 不出现“功能说明型大段文字”。

### 8.2 功能验收

1. 登录 ecommerce 组织后直接看到 Seller 工作台。
2. 登录非 ecommerce 组织后看不到 Seller 工作台。
3. 库存、流水、摘要能刷新。
4. 入库/出库成功后，库存、流水、摘要自动更新。
5. AI 能回答库存、低库存、销售收入、采购支出。
6. AI 写入意图仍被拒绝。

### 8.3 安全验收

1. 前端请求不传 `organization_id`、`person_id`、`resource_id`、`warehouse_id`、`transaction_id`。
2. 前端展示不出现 `id`、`*_id`、`pid`、`oid`。
3. Seller AI 只调用 Seller 安全只读工具。
4. 默认测试不触发真 LLM。

## 10. 红线

以下任一情况出现，BE-05 不允许合并：

1. 前端仍以旧 Tabs 堆叠作为卖家主界面。

3. 入库/出库表单要求用户填写内部主键。
4. ecommerce 用户能绕过 Seller 工作台调用通用 AI。
5. 默认测试触发真 LLM。
6. 未做 3 个静态 demo 就直接重构实现。
