# CR-01 开发规格书：多业务空间参赛生产版

> 日期：2026-08-03
> 角色：PM / 产品负责人
> 状态：下达给开发团队，完成后进入生产环境参赛交付
> 定位：比赛亮点收口版，不再做大范围架构重写。

## 1. 产品目标

参赛版要让评委一眼看懂 Uni-Resource Agent 的核心价值：

**一个账号，一个人，可以进入多个业务空间；不同空间有不同资源、人员、事件、资金和 AI 能力。**

这里的“一个账号”指 `account.login`，不是 `puid@ouid` 组合账号。参赛演示账号统一为 `zhansan`，其业务人员身份为 `person.puid=zhansan`，可进入的业务空间由 `membership` 决定。

本版不是只交付一个淘宝卖家库存后台，而是交付一个可切换的多空间资源智能体：

1. 淘宝卖家空间：真实经营闭环，库存、商品、入库、出库、流水、摘要、Seller AI。
2. 火烧新野空间：战役复盘，时间线、阵营、人物、物资、资金、事件流。
3. 家庭学习空间：家庭成员、孩子学习任务、资料、预算、提醒式观察。
4. 科幻战舰空间：原创深空舰队场景，舰员、舱段、能源、物资、任务、风险观察。

这四类空间共同证明产品的参赛亮点：**Everything is a Resource + Multi-Context Space**。

## 2. 核心产品原则

1. `AppHeader` 是空间上下文层：用户、当前空间、空间类型、角色、空间切换、空间治理入口。
2. Sidebar 是当前空间内的应用导航。
3. Main 是当前业务空间的工作台。
4. AI 不放在 Header 里；Header 不提供 AI button，AI 只保留在 Sidebar / 业务主区。
5. Seller 是可操作业务空间；其他空间本版以观察和复盘为主。
6. 所有前端和 API 响应继续坚持不暴露 DB 数字 ID，不恢复 `pid/oid` 兼容。
7. 登录和注册不得把 `account.login` 解析为组织上下文；空间上下文只能来自 membership 校验后签发的 JWT。

## 3. 参赛版 P0 范围

### 3.1 Header 与空间治理入口

调整现有 `AppHeader`：

1. 保留当前用户、`puid`、当前组织名、`ouid`、空间类型、组织角色。
2. 保留组织切换下拉，切换必须通过新 JWT。
3. 移除完整 AI 输入框和「问 AI」按钮。
4. 增加小入口：
   - `AI`：进入当前空间的 AI 页；ecommerce 才接 `/seller/chat`。
   - `空间`：打开空间菜单。
5. 空间菜单 MVP 项：
   - 管理空间
   - 加入空间
   - 审核申请
   - 退出空间
6. 空间治理项本版可先进入占位视图，不做真实写操作。

验收：Header 第一眼必须能看出「我是谁、在哪个空间、是什么业务形态、能切到哪里」。

登录态要求：用户只登录一次 `zhansan`，不能通过 `zhansan@fire_xinye_shu`、`zhansan@zhangsan_family` 等多账号切换空间。

### 3.2 Seller 商品管理

Seller 空间必须补商品主数据，否则库存系统不像完整产品。

新增 Seller「商品」视图：

1. 商品列表：
   - `product_uid`
   - 单位
   - 状态 active/inactive
   - 当前库存总数
   - 库位数
2. 新增商品：
   - `product_uid`
   - 单位
   - 描述可选
3. 停用商品：
   - 不删除历史流水。
   - 默认入库/出库选择不显示 inactive 商品。
4. 入库/出库弹窗：
   - `product_uid` 改为可搜索选择。
   - 手动输入未知商品时必须明确提示，避免错别字直接生成脏数据。

后端建议新增 Seller 安全 API：

```text
GET  /seller/products
POST /seller/products
PATCH /seller/products/{product_uid}
```

响应和请求都只允许业务字段，不得出现 `id`、`resource_id`、`organization_id`、`person_id`、`pid`、`oid`。`product_uid` 即商品业务名/编号，本版不新增独立商品 `name` 字段。

### 3.3 通用空间观察面板

非 ecommerce 空间不再只显示「暂未接入」，而是显示通用观察面板。

适用空间：`military`、`family`、`campaign`、`starship`、其他未专门接入的组织类型。

通用观察面板包含：

1. 空间概览：
   - 空间名称、类型、角色
   - 资源数量
   - 人员数量
   - 交易/资金事件数量
   - 最近事件数量
2. 资源观察：
   - physical / knowledge / financial / human 分组
   - 名称、类型、数量/金额、单位、说明
3. 人员观察：
   - 成员名、`puid`、角色
4. 时间线：
   - 复用 campaign replay 数据，有则显示事件序列
   - 没有事件时显示空状态
5. 多维流向：
   - 信息流：knowledge 资源和事件说明
   - 物流：physical 资源和仓库/库位
   - 人流：membership 和事件参与方
   - 资金流：`/spaces/current/transactions` 明细 + `/spaces/current/overview` funds

MVP 不要求画复杂拓扑图，先用四个分组面板和事件时间线呈现。

### 3.4 示例空间包

复用现有 `data/campaigns/*.json` 和 `/campaigns/import` 机制，前端产品文案统一称为「示例空间包」。

新增或完善 3 个空间包：

1. `fire_xinye.json`
   - 已存在，补齐事件 payload 的维度标签：`info_flow`、`logistics_flow`、`people_flow`、`risk`。
2. `family_learning.json`
   - 组织：`zhangsan_family`
   - 类型：`family`
   - 人员：父母、孩子
   - 资源：学习计划、教材、课程费用、错题本、阅读任务
   - 事件：每日学习要求、作业检查、阶段总结
3. `deep_space_fleet.json`
   - 组织：`deep_space_fleet`
   - 类型：`starship`
   - 使用原创设定，避免直接使用受版权保护的专有世界观和名称
   - 资源：能源、氧气、水、维修备件、知识库、舰员职责
   - 事件：航行、故障、补给、风险处置

参赛生产环境必须预置这些示例空间，保证演示时无需现场导入。

## 4. 建议实现方式

### 4.1 后端

1. 保留现有 `organization.type` 作为 workspace 类型，不新增 `workspace` 表。
2. `campaign_import` 继续作为示例空间包导入记录，不做大重命名。
3. 新增 Seller 商品 API。
4. 新增只读聚合接口支撑观察面板，不复用会泄漏 DB 字段或含公开上下文兜底的旧接口：

```text
GET /spaces/current/overview
GET /spaces/current/resources
GET /spaces/current/persons
GET /spaces/current/transactions
GET /spaces/current/timeline
```

这些接口必须从 JWT 获取当前空间，不接受身份参数。非 ecommerce 观察面板不得调用旧 `/summary`、`/transactions`。

### 4.2 前端

1. Header 调整为上下文和治理入口。
2. Sidebar 根据 `orgType` 动态显示导航：
   - ecommerce：工作台、商品、库存、库存流水、经营摘要、Seller AI
   - non-ecommerce：空间总览、资源、人员、时间线、多维观察
3. 新增 `GenericSpaceView`，承载非 Seller 空间。
4. 新增 `ProductsView`，承载 Seller 商品管理。
5. 新增「示例空间包」入口，生产环境可只展示已预置状态，不要求普通用户导入。

### 4.3 数据

1. 扩展 `data/campaigns/` 示例 JSON。
2. 初始化脚本或部署脚本负责预置参赛空间。
3. 不把真实密钥、真实个人信息写入示例数据。
4. 科幻战舰场景使用原创名称，例如「深空远航舰队」，不直接使用第三方受保护名称。

### 4.4 认证与注册

1. 模型固定为 `account -> person -> membership -> organization`。
2. `account.login` 是登录凭据，`person.puid` 是业务人员标识，二者不物理归并；MVP 演示可同值。
3. 注册接口创建 `account + person`，可选加入初始组织；未加入组织时进入“暂无业务空间”占位态。
4. 登录接口只接收 `login/password`，不从 login 解析 `ouid`。
5. 切换空间必须调用 `/auth/switch-organization`，由后端校验 membership 后重新签发 JWT。
6. 参赛种子脚本只创建一个 `account.login=zhansan`，并建立到 4 个演示空间的 membership。

## 6. 演示脚本

比赛演示按以下顺序：

1. 登录 `zhansan`，Header 显示当前用户和当前空间。
2. 进入淘宝卖家空间：展示销售、采购、库存、低库存、商品管理、Seller AI。
3. 切换到火烧新野空间：展示时间线、阵营、人物、物资、资金流。
4. 切换到家庭学习空间：展示孩子学习任务、资料、费用和家庭成员。
5. 切换到深空舰队空间：展示舰员、能源、物资、风险事件。
6. 总结：同一个系统没有换账号，只切换业务空间，AI 和数据权限随空间变化。

## 8. 生产上线红线

以下任一项未满足，不允许上生产参赛：

1. Header 无法切换多个空间。
2. Seller 缺商品管理。
3. 非 ecommerce 空间仍只显示「暂未接入」。
4. 切换非 ecommerce 后仍调用 `/seller/*`。
5. 业务端出现 DB 数字 ID。
6. 前端或文档提交真实密钥。
7. 默认测试触发真 LLM。
8. 生产环境没有预置示例空间数据。
9. 演示账号仍依赖 `zhansan@<ouid>` 多账号方式。

## 9. PM 最终判断

完成 CR-01 后，产品具备参赛亮点：

1. 有真实可操作的小店经营场景。
2. 有火烧新野的多维复盘场景。
3. 有家庭学习管理场景，贴近日常生活。
4. 有原创科幻舰队场景，展示系统抽象能力。
5. 同一个账号跨空间切换，明确体现 MCS，不再像普通单一后台。

CR-01 完成并通过安全扫描后，可以进入生产环境参加比赛。
