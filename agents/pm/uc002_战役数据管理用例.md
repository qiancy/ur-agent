# 战役数据管理用例

> 角色：项目经理  
> 状态：待开发实现  
> 范围：战役模板导入、战役数据列表、战役回放、战役数据删除  
> 约束：默认新增 `super` 系统超级用户；普通用户只能查看所属组织数据；导入数据必须可按批次删除。

---

## 1. 目标

主界面需要增加战役模拟数据列表，例如“火烧新野”。管理员或超级用户可以从 JSON 导入测试战役数据，导入后数据通过后端 API 写入数据库。普通用户只能查看自己所属组织的数据，超级用户可以查看全部数据，并可以删除导入的战役数据。

本用例用于指导开发团队实现：

1. 系统默认超级用户 `super`。
2. 战役模板 JSON 管理。
3. 战役导入 API。
4. 战役列表与回放 API。
5. 战役批次删除 API。
6. 前端主界面展示与权限控制。

---

## 2. 角色与权限

### super 系统全局超级用户

`super` 是系统全局级别超级用户，权限作用域是整个系统，不属于某个业务组织权限，也不受单个组织 membership 限制。系统初始化时必须默认创建一个开发用超级账号：

```text
super@system.cn / demo123
```

初始化要求：

1. 创建 `person.puid = super`，`person.name = 超级用户`。
2. 创建 `organization.ouid = system`，`organization.name = 系统空间`，`organization.type = system`。
3. 创建 `account.login = super@system.cn`，密码使用 `account.password` 保存哈希，禁止明文存储。
4. 创建 `account.system_role = super`。
5. 创建 `membership(person=super, organization=system, role=admin)`，仅作为 system 组织内角色。
6. 生产环境必须修改默认密码，或通过环境变量禁用默认密码。


JWT 要求：

```json
{
  "puid": "super",
  "ouid": "system",
  "system_role": "super",
  "role": "admin"
}
```

JWT 只允许包含业务字段 `puid`、`ouid`、`system_role`、`role` 等，不得包含 `person_id`、`org_id`、`organization_id`、`person_puid` 等数据库内部字段或混合字段。`system_role` 来自 `account.system_role`，`role` 来自当前组织的 `membership.role`。

### 普通用户

普通用户通过 `membership` 获得组织访问权限，只能查看自己所属组织的数据。

普通用户可以：

1. 查看自己所属组织的战役数据。
2. 查看自己所属组织的交易、参与方、资源、仓库等业务数据。
3. 使用回放功能查看自己有权限访问的战役事件。

普通用户不可以：

1. 查看其他组织的数据。
2. 导入战役数据。
3. 删除战役数据。
4. 在注册时自己提交 `super`、`admin` 等特权角色。

### admin 组织级管理员

`admin` 是组织级别角色，保存在 `membership.role`，只在一条 `membership(person_id, organization_id, role=admin)` 对应的组织内生效。`admin` 不是系统管理员，不能等同于 `account.system_role = super`。

管理员权限建议：

1. `role=admin` 可以管理自己所属组织内的数据。
2. `role=admin` 只能访问自己有 membership 的组织。
3. `role=admin` 不能跨组织查看所有数据。
4. `role=admin` 不能导入全局战役模板，除非后续明确设计为“导入到本组织”。
5. `role=admin` 不能删除不属于自己组织的战役批次。

MVP 阶段建议只开放 `super` 执行战役导入和删除，避免组织级 admin 与全局管理权限混淆。

## 3. 数据模型建议

### campaign_import

记录一次战役导入批次。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | integer | 数字主键 |
| `campaign_code` | varchar | 战役模板编码，例如 `fire_xinye` |
| `campaign_name` | varchar | 战役名称，例如 `火烧新野` |
| `source_file` | varchar | 导入来源，例如 `data/campaigns/fire_xinye.json` |
| `imported_by_puid` | varchar | 导入人业务标识，例如 `super` |
| `status` | varchar | `active` / `deleted` |
| `created_at` | timestamp | 导入时间 |
| `deleted_at` | timestamp | 删除时间，可空 |

注意：`imported_by_puid` 是审计字段，可以保存业务 puid。业务数据表之间的关联仍使用数据库外键，不用 puid/ouid 代替外键。

### campaign_import_org

记录战役批次生成或关联的组织。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | integer | 数字主键 |
| `campaign_import_id` | integer | 外键，指向 `campaign_import.id` |
| `organization_id` | integer | 外键，指向 `organization.id` |
| `created_by_import` | boolean | 是否由本次导入创建 |

删除战役批次时，只删除 `created_by_import = true` 的导入组织及其业务数据。不要删除 `person` 和 `account`，避免误删复用用户身份。

### campaign_event

记录战役回放事件。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | integer | 数字主键 |
| `campaign_import_id` | integer | 外键，指向 `campaign_import.id` |
| `organization_id` | integer | 外键，指向 `organization.id` |
| `seq` | integer | 回放顺序 |
| `title` | varchar | 事件标题 |
| `description` | text | 事件描述 |
| `payload` | jsonb | 原始事件数据 |
| `created_at` | timestamp | 创建时间 |

`organization_id` 用于权限过滤。普通用户只能看到自己有 membership 的组织事件；`super` 可以查看全部事件。

## 4. 战役模板 JSON

新增目录：

```text
data/campaigns/
```

新增模板：

```text
data/campaigns/fire_xinye.json
```

模板至少包含：

1. `campaign_code`：`fire_xinye`
2. `campaign_name`：`火烧新野`
3. `organizations`：战役涉及组织，例如 `liu_beijun`、`caojun`
4. `persons`：战役人物，例如 `liubei`、`zhugeliang`、`caocao`
5. `memberships`：人物与组织关系
6. `parties`：交易或资源流转参与方，参与方有方向性
7. `resources`：资源、兵力、粮草、装备等
8. `transactions`：交易或资源流转记录
9. `events`：回放事件列表

参与方方向要求：

1. 一个交易可以有多个参与方。
2. 参与方必须有方向字段，例如 `direction = out` 表示支出，`direction = in` 表示收入。
3. 前端展示时使用 `-` 表示支出，用 `+` 表示收入。
4. 交易和参与方应该在同一个界面展示，不拆成两个孤立页面。

## 5. API 设计

### 查询可导入战役模板

```http
GET /campaigns/templates
```

权限：

1. 登录用户可查看模板列表。
2. 是否可导入由前端根据角色展示按钮，后端仍必须强校验。

Response 示例：

```json
[
  {
    "campaign_code": "fire_xinye",
    "campaign_name": "火烧新野",
    "source_file": "data/campaigns/fire_xinye.json"
  }
]
```

### 导入战役

```http
POST /campaigns/import
```

权限：

1. `system_role=super` 可以导入所有战役模板。
2. MVP 阶段可以先只允许系统角色 `super` 导入。
3. 后端必须从 JWT 读取 `puid`、`ouid`、`system_role`、`role`，不能信任前端提交的角色。

Request：

```json
{
  "campaign_code": "fire_xinye"
}
```

业务流程：

1. 校验 JWT，确认 `system_role=super`。
2. 读取 `data/campaigns/fire_xinye.json`。
3. 创建 `campaign_import` 批次。
4. 创建或复用 `organization`，写入 `campaign_import_org`。
5. 创建或复用 `person`，创建 `membership`。
6. 写入资源、仓库、交易、参与方和回放事件。
7. 返回导入批次信息。

### 查询战役导入列表

```http
GET /campaigns/imports
```

权限：

1. `super` 返回全部 active 批次。
2. 普通用户只返回包含自己所属组织的批次。

### 查询战役回放

```http
GET /campaigns/imports/{campaign_import_id}/replay
```

权限：

1. `super` 可查看全部事件。
2. 普通用户只能查看自己所属组织的事件。

Response 示例：

```json
{
  "campaign_import_id": 1,
  "campaign_name": "火烧新野",
  "events": [
    {
      "seq": 1,
      "title": "曹军南下",
      "description": "曹军逼近新野，刘备军开始转移资源。",
      "organization": {
        "ouid": "caojun",
        "name": "曹军"
      }
    }
  ]
}
```

### 删除战役导入

```http
DELETE /campaigns/imports/{campaign_import_id}
```

权限：

1. MVP 阶段只允许 `super` 删除。
2. 后续可允许组织级 `admin` 删除自己所属组织内的导入数据，但不能影响其他组织。

删除规则：

1. 软删除 `campaign_import.status = deleted`。
2. 删除该批次的 `campaign_event`。
3. 删除该批次导入产生的资源、仓库、交易、参与方等业务数据。
4. 删除 `campaign_import_org.created_by_import = true` 的组织及其级联业务数据。
5. 不删除 `person`。
6. 不删除 `account`。
7. 不删除非本批次创建的组织。

## 6. 前端组织方式

未登录时：

1. 显示网站主界面。
2. 主界面有登录按钮。
3. 登录按钮打开用户登录界面。
4. 登录界面提供注册入口。

登录后：

1. 显示当前用户和当前组织。
2. 普通用户只显示当前组织和所属组织的数据。
3. `super` 显示“全部组织”视角。
4. 主界面展示战役模拟数据列表，例如“火烧新野”。
5. 点击战役进入回放界面。
6. 交易和参与方放在同一个界面，参与方按 `+` 收入、`-` 支出展示。

`super` 专属操作：

1. 显示导入战役按钮。
2. 显示删除战役按钮。
3. 可以查看所有组织的战役、资源、交易和参与方数据。

普通用户：

1. 不显示导入按钮。
2. 不显示删除按钮。
3. 不显示无权限组织数据。

## 8. 验收标准

1. `super@system.cn / demo123` 可以登录。
2. `super` 登录后 JWT 中包含 `puid=super`、`ouid=system`、`system_role=super`、`role=admin`，不包含数据库数字 ID。
3. `super` 可以导入“火烧新野”战役。
4. 导入后普通用户只能看到自己所属组织的数据。
5. `super` 可以查看所有组织数据。
6. 战役回放按事件顺序展示。
7. 交易和多个参与方在同一界面展示，收入为 `+`，支出为 `-`。
8. `super` 可以删除导入批次。
9. 删除导入批次后，相关战役业务数据不可见。
10. 删除导入批次后，`person` 和 `account` 不被删除。
