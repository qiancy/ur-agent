# 淘宝卖家仓库系统用例

> 角色：项目经理  
> 日期：2026-07-29  
> 范围：中小淘宝卖家的轻量仓库、进销存、库位和资金流水  
> 目标：证明 Uni-Resource Agent 可以先解决真实小组织的高频资源管理问题。

## 1. 目标组织

目标组织是中小淘宝卖家或家庭式电商团队。典型规模为 1-10 人，仓库可能是家中房间、小仓、档口、共享仓或办公室角落。

老大是店主或仓库负责人。其核心目标是：

1. 知道每个货品有多少、放在哪里。
2. 记录进货、售出、退货、损耗和盘点差异。
3. 让库存变化和资金流水能对得上。
4. 在不引入重型 ERP 的情况下，用自然语言快速查询和录入。

## 2. 系统边界

MVP 不做完整电商平台，不对接淘宝开放平台，不处理订单自动同步、物流面单、发票、客服和广告投放。

MVP 只承诺：

1. 管理商品资源。
2. 管理仓库和库位。
3. 记录进货入库。
4. 记录销售出库。
5. 记录退货入库。
6. 记录损耗或报废。
7. 查询库存和库位。
8. 汇总资金和库存变化。
9. 通过 AI 助手执行上述查询和录入。

## 3. 执行者

| 执行者 | 说明 |
|------|------|
| 店主 | 组织 owner，关注库存、现金流和补货 |
| 仓库负责人 | 组织 admin/member，负责入库、出库、盘点和库位维护 |
| 发货员 | 组织 member，负责销售出库和退货入库 |
| AI 助手 | 系统内部代理，按当前 `ouid` / `puid` 上下文调用工具 |

权限要求：

1. 所有业务数据必须绑定当前登录用户 JWT 中的 `ouid`。
2. 普通成员只能操作自己所属店铺组织。
3. 前端传入的 `ouid`、`resource_id`、`warehouse_id` 不能绕过 JWT 权限。
4. `person.id`、`organization.id` 等数字主键只作为内部实现细节。

## 4. 领域对象

| 对象 | 建议映射 |
|------|------|
| 店铺 | `organization(type=ecommerce)` |
| 店主/员工 | `person` + `membership` |
| 商品/SKU | `resource(type=physical)` |
| 现金账户 | `resource(type=financial)` 或 `organization.funds` |
| 仓库 | `warehouse` |
| 库位库存 | `resource_warehouse` |
| 进货/销售/退货/损耗 | `transaction` + `party` + 库存变动记录 |

MVP 可先用 `resource.name` 表示商品名，用 `resource.unit` 表示单位，用 `resource.content` 或后续扩展字段保存规格。后续再扩展 SKU 编码、条码、成本价、售价、供应商和平台订单号。

## 6. 核心用例规约

### TB003 创建商品资源

执行者：店主、仓库负责人

前置条件：

1. 用户已登录。
2. 用户属于当前店铺组织。

基本路径：

1. 执行者输入商品名称、单位、规格说明。
2. 系统在当前 `organization_id` 下创建 `resource(type=physical)`。
3. 系统返回商品资源 ID 和商品信息。

后置条件：

1. 商品只在当前店铺可见。
2. 其他店铺查询不到该商品。

异常路径：

1. 商品名为空，系统拒绝创建。
2. 同一店铺已有同名同规格商品，系统提示复用或修改。

### TB004 创建仓库和库位

执行者：店主、仓库负责人

基本路径：

1. 执行者创建仓库，例如“家中仓”“档口仓”。
2. 执行者维护库位路径，例如 `A-01-03`、`客厅-货架1-箱2`。
3. 系统保存仓库和库位，库位用于库存明细。

后置条件：

1. 仓库属于当前店铺组织。
2. 库位库存必须引用当前店铺的商品资源。

### TB005 进货入库

执行者：店主、仓库负责人

基本路径：

1. 执行者选择商品、数量、单位、入库库位、采购金额、供应商和备注。
2. 系统校验商品属于当前店铺。
3. 系统校验入库数量和采购金额为正数。
4. 系统增加指定库位库存。
5. 系统记录采购交易，店铺资金减少。
6. 系统返回入库结果、当前库存和资金变化。

后置条件：

1. 商品总库存增加。
2. 指定库位库存增加。
3. 资金流水产生一笔采购支出。
4. 库存变化和交易记录可追溯到同一次业务操作。

异常路径：

1. 商品不存在，系统拒绝入库。
2. 库位不存在，系统提示先创建或自动创建。
3. 数量小于等于 0，系统拒绝入库。

### TB006 销售出库

执行者：店主、发货员

基本路径：

1. 执行者选择商品、数量、出库库位、销售金额、客户或订单备注。
2. 系统校验商品属于当前店铺。
3. 系统校验指定库位库存充足。
4. 系统扣减指定库位库存。
5. 系统记录销售交易，店铺资金增加。
6. 系统返回出库结果、当前库存和资金变化。

后置条件：

1. 商品总库存减少。
2. 指定库位库存减少。
3. 资金流水产生一笔销售收入。
4. 库存不得出现负数。

异常路径：

1. 库存不足，系统拒绝出库。
2. 出库商品不属于当前店铺，系统拒绝操作。
3. 销售金额小于 0，系统拒绝记录。

### TB009 查询库存和库位

执行者：店主、仓库负责人、发货员

基本路径：

1. 执行者输入商品名或商品 ID。
2. 系统按当前店铺组织查询商品。
3. 系统返回总库存、库位分布和单位。

后置条件：

1. 查询结果只包含当前店铺数据。
2. 能回答“某款商品还剩多少”“放在哪里”。

### TB012 查询经营摘要

执行者：店主

基本路径：

1. 执行者请求经营摘要。
2. 系统统计当前店铺销售收入、采购支出、交易笔数、库存总件数和低库存商品。
3. 系统返回摘要。

后置条件：

1. 摘要只基于当前店铺数据。
2. 收入、支出和库存变化口径一致。

### TB013 AI 自然语言操作

执行者：店主、仓库负责人、发货员

示例：

```text
今天进了 20 件白色手机壳，放在 A-01-03，花了 160 元。
卖出 3 件白色手机壳，收入 45 元，从 A-01-03 发货。
白色手机壳还剩多少，分别在哪些库位？
哪些商品库存少于 5 件？
今天销售额和采购支出分别是多少？
```

基本路径：

1. AI 助手识别当前 JWT 上下文。
2. AI 助手解析商品、数量、库位、金额和业务类型。
3. AI 助手调用受权限保护的库存和交易工具。
4. 系统返回可核对的结构化结果。

验收要求：

1. AI 不能使用默认 `ouid` 越权查询。
2. AI 不能直接操作其他店铺资源 ID。
3. AI 操作失败时必须说明缺少哪些字段。

## 7. API 建议

建议新增业务级 API，避免前端和 AI 分多步调用底层资源接口造成不一致。

| 方法 | 路径 | 用途 |
|------|------|------|
| POST | `/seller/products` | 创建商品 |
| GET | `/seller/products` | 查询商品 |
| POST | `/seller/warehouses` | 创建仓库 |
| POST | `/seller/purchase-in` | 进货入库 |
| POST | `/seller/sales-out` | 销售出库 |
| POST | `/seller/returns-in` | 退货入库 |
| POST | `/seller/stock-adjustments` | 盘点、损耗和报废 |
| GET | `/seller/stock` | 查询库存和库位 |
| GET | `/seller/summary` | 查询经营摘要 |

这些 API 内部可以复用现有 `resource`、`warehouse`、`resource_warehouse`、`transaction`、`party` 表，但必须在一个数据库事务中同时完成库存变化和交易记录。

## 8. 验收标准

1. 店主可以创建店铺、商品、仓库和库位。
2. 进货入库会增加库存并记录采购支出。
3. 销售出库会减少库存并记录销售收入。
4. 出库库存不足时不能扣成负数。
5. 查询库存可以看到总数和库位分布。
6. 经营摘要能看到收入、支出、交易数和库存概览。
7. 普通用户不能通过 `resource_id` 查询或修改其他店铺库存。
8. AI 助手能完成至少三条自然语言命令：入库、出库、查库存。
9. 所有数据访问必须以 JWT 中的 `ouid` 为准，前端提交的 `ouid` 只能作为显示或 demo 查询上下文，不作为授权依据。
