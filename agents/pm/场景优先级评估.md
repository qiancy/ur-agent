# 场景优先级评估

> 角色：项目经理  
> 日期：2026-07-29  
> 结论：产品 MVP 应最先满足淘宝卖家的轻量仓库场景；火烧新野优先作为演示和回归测试场景；蓝色空间号作为未来扩展或压力测试场景。

## 1. 评估口径

项目经理对产品价值和生命负责，因此优先级不只看场景是否有趣，而看它是否能证明产品能活下去。

评估维度：

| 维度 | 含义 |
|------|------|
| 目标组织匹配度 | 是否贴合“数据敏感、资源分散、没有重型 ERP 能力的中小组织” |
| 痛点强度 | 是否存在高频、明确、愿意付费或持续使用的问题 |
| MVP 实现成本 | 是否能用现有资源、仓库、交易、人员、知识模型快速落地 |
| 演示效果 | 是否能在比赛演示中快速说明系统价值 |
| 复用性 | 是否能沉淀为通用能力，而不是只服务单一剧情 |

## 2. 场景排序

| 排名 | 场景 | 定位 | 判断 |
|------|------|------|------|
| 1 | 淘宝卖家的仓库功能 | 第一业务 MVP | 最贴近真实付费组织，买入、卖出、货品位置和收支都是高频刚需 |
| 2 | 火烧新野战役复现 | 第一演示和回归测试场景 | 已有故事、测试和用例基础，适合展示信息流、物流、人流，但不是直接付费组织 |
| 3 | 三体“蓝色空间号”飞船管理系统 | 未来概念扩展 | 展示空间大，但过于虚构，范围容易失控，不适合作为 MVP 起点 |

## 3. 场景分析

### 淘宝卖家的仓库功能

这是最应该优先满足的真实业务场景。

目标组织是小电商卖家或家庭式电商团队。老大是店主或仓库负责人。他们每天面对的问题是：进了多少货、卖了多少货、货放在哪里、哪些快缺货、现金流是否正常、订单和库存是否对得上。

系统买点清晰：
- 查询货品位置和库存数量。
- 记录进货、售出、退货和损耗。
- 关联交易和库存变化。
- 用自然语言问“某款商品还剩多少”“今天卖出了哪些货”“哪些货需要补”。

它最贴合 Uni-Resource Agent 的产品定位：小组织、真实资源、高频操作、轻量替代 Excel 和人工记账。

### 火烧新野战役复现

这是当前最适合保留和强化的演示/测试场景。

它能同时覆盖：
- 时间线：曹军逼近、诱敌、布置火攻、撤退、复盘。
- 阵营：刘备军、曹军、百姓、后勤队。
- 任务：侦查、调拨、放火、转移、补给。
- 活动：命令下达、物资搬运、人员移动、事件回放。
- 物资：粮草、火油、火把、兵器、马匹。
- 信息流、物流、人流：谁知道什么、物资从哪里到哪里、人员从哪里移动到哪里。

它的优势是演示效果强，已有测试资产和文档基础，能证明系统“万物皆资源”的建模能力。但它不是直接付费场景，不能作为产品存活的第一目标组织。

### 三体“蓝色空间号”飞船管理系统

这个场景适合以后做高级概念展示，不适合先做。

原因：
- 目标组织虚构，无法验证真实购买意愿。
- 资源类型会急剧膨胀，例如生命维持、航行、舰员心理、能源、武器、权限、危机决策。
- 需求边界大，容易把 MVP 拉成复杂仿真系统。
- 对当前代码的近期收益不如淘宝仓库和火烧新野。

它可以作为未来压力测试：验证系统是否能处理极端复杂的多资源、多角色、多事件场景。

## 4. PM 决策

最先满足：**淘宝卖家的仓库功能**。

近期执行顺序：

1. 将淘宝卖家仓库作为真实业务 MVP：买入、卖出、库存位置、库存汇总、交易流水。
2. 保留火烧新野作为演示和回归测试：用它展示系统能复盘复杂事件中的信息流、物流、人流。
3. 暂不投入蓝色空间号：只保留为未来扩展方向，不进入当前迭代。

对应产品叙事：

> 我们不是先做一个科幻管理系统，也不是只做历史战役回放。我们先解决小组织真实的资源管理问题，再用火烧新野证明同一套资源模型可以复盘复杂事件。
