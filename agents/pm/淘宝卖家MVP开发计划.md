# 淘宝卖家 MVP 开发计划

> 角色：项目经理  
> 日期：2026-07-29  
> 对应用例：`agents/pm/uc003_淘宝卖家仓库用例.md`  
> 目标：优先交付中小淘宝卖家的轻量仓库 MVP，证明产品能解决真实小组织的高频资源管理问题。

## 1. MVP 范围

本轮只做 P0：

| 用例 | 名称 | 本轮要求 |
|------|------|------|
| TB001 | 创建店铺空间 | 支持 `organization(type=ecommerce)` |
| TB003 | 创建商品资源 | 支持商品名、单位、规格说明 |
| TB004 | 创建仓库和库位 | 支持仓库和库位库存 |
| TB005 | 进货入库 | 增加库存并记录采购支出 |
| TB006 | 销售出库 | 扣减库存并记录销售收入 |
| TB009 | 查询库存和库位 | 返回总库存和库位分布 |
| TB012 | 查询经营摘要 | 返回收入、支出、交易数和库存概览 |
| TB013 | AI 自然语言操作 | 支持入库、出库、查库存三类命令 |

本轮不做：

1. 淘宝开放平台对接。
2. 订单自动同步。
3. 物流面单。
4. 发票、客服、广告投放。
5. 多规格 SKU 完整商品中心。

## 3. 任务拆分

### BE-01 权限隔离收口

负责人：后端负责人  
优先级：P0  
计划日期：2026-07-29

任务：

1. 所有写接口必须要求 Bearer JWT。
2. 淘宝卖家 MVP 接口不得接受前端传入的 `organization_id`。
3. `resource_id`、`warehouse_id`、`transaction_id` 必须校验属于当前 JWT `ouid`。
4. 非 ecommerce demo 可显式传 `?ouid=shu`；Seller P0 必须使用 JWT 上下文。

交付件：

1. `src/routers/deps.py` 增加严格上下文依赖，例如 `require_strict_org_context`。
2. Seller API 全部使用严格上下文。
3. 增加越权访问测试。

### BE-02 库存业务事务

负责人：后端负责人  
优先级：P0  
计划日期：2026-07-30

任务：

1. 增加库存变动 helper：入库加库存、出库扣库存。
2. 出库必须在数据库事务内校验库存充足。
3. 库存不得出现负数。
4. 同一次业务操作必须同时写库存变化和交易记录。

建议实现：

1. 新增 `inventory_movement` 表记录库存流水。
2. `purchase_in`、`sales_out` 使用同一个数据库连接和事务提交。
3. 对目标 `resource_warehouse` 行使用 `SELECT ... FOR UPDATE` 或等价锁。

交付件：

1. `src/db/database.py` 增加库存事务函数。
2. `src/routers/seller.py` 提供业务级接口。
3. 测试覆盖库存不足、重复库位、跨组织资源 ID。

### BE-03 Seller API

负责人：后端负责人  
优先级：P0  
计划日期：2026-07-30 至 2026-07-31

接口：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/seller/products` | 创建商品 |
| GET | `/seller/products` | 查询商品 |
| POST | `/seller/warehouses` | 创建仓库 |
| POST | `/seller/purchase-in` | 进货入库 |
| POST | `/seller/sales-out` | 销售出库 |
| GET | `/seller/stock` | 查询库存和库位 |
| GET | `/seller/summary` | 查询经营摘要 |

交付件：

1. `src/models/schemas.py` 增加 Seller 请求模型。
2. `src/routers/seller.py` 增加 Seller 路由。
3. `src/app.py` 注册 Seller 路由。
4. `docs/API.md` 增加 Seller API 文档。

## 5. 风险和裁决

| 风险 | 影响 | 裁决 |
|------|------|------|
| 权限隔离不严 | 产品不能用于真实店铺 | Seller P0 不接受无 JWT 写操作 |
| 库存和交易分步提交 | 数据对不上，失去信任 | 入库/出库必须后端事务化 |
| AI 使用默认 `ouid` | 可能跨店铺操作 | AI 工具由服务端绑定上下文 |
| 前端范围过大 | 赶不上交付 | 只做工作台，不做电商平台 |
| 老测试与新 schema 冲突 | 测试结果失真 | Seller 新测试作为 MVP 验收依据 |

## 6. 开发顺序

严格顺序：

1. 先修权限。
2. 再做库存事务。
3. 再做 Seller API。
4. 再做前端和 AI。
5. 最后做演示和包装。

原因：如果权限和库存事务不先收口，前端和 AI 做得越多，返工越多。
