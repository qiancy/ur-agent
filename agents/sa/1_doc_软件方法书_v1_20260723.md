# 软件方法书

本文件由 潘加宇老师的《软件方法》精简而来。保留方法、定义、判断标准、步骤和常见错误；删除前言、致谢、歌词、宣传、工具操作截图说明、练习题、长篇类比和大段故事。

## 1. 建模和 UML

### 1.1 核心公式

软件开发的目标可以简化为：

```text
利润 = 需求 - 设计
```

这里的“需求”不是指某份需求文档，而是指需求工作创造的对外价值和收入空间；“设计”不是指某份设计文档，而是指设计工作控制的制造、修改、维护成本。

含义：

- 需求工作解决“卖什么才有价值”，目的是提高收入。
- 设计工作解决“怎样低成本制造和维护”，目的是降低成本。
- 需求和设计不能互相代替。

常见混淆：

- 把功能需求包叫“子系统”。
- 从需求直接映射设计，得到“走路子系统、跑步子系统”式的重复结构。
- 从设计反推需求，得到“心管理、肝管理”式的假需求。

### 1.2 四个建模工作流

1. 业务建模：研究组织内部各系统如何协作，让组织对外提供价值。软件只是组织新增或替换的一个零件。
2. 需求：描述系统为解决组织问题必须对外表现出的功能和质量。
3. 分析：提炼系统为满足功能需求必须封装的核心域机制。
4. 设计：把核心域机制映射到具体平台、技术、质量约束和实现结构。

区别不在图形形式，而在思考边界：

- 业务建模：系统在组织中如何发挥作用。
- 需求：系统作为黑箱对外提供什么价值。
- 分析：系统内部应封装哪些核心域概念和关系。
- 设计：这些概念如何映射到数据库、界面、代码、进程、网络等实现。

### 1.3 UML 的位置

UML 是软件开发团队内部沟通的建模语言，不是拿来直接和涉众沟通的万能介质。

使用原则：

- 只使用项目需要的 UML 元素，不追求全量使用。
- 模型按工作流组织，比按图形种类组织更能减少思维跳层。
- 模型必须体现思考结果；如果还需要建模者口头先讲一遍才看懂，说明模型表达不足。
- UML 模型主要服务开发团队内部共识。与涉众沟通时，应输出合适的视图，例如幻灯片、文档、原型、访谈提纲或演示。

### 1.4 建模和敏捷

敏捷不是放弃建模的理由。迭代只是承认一次做不完，每个迭代内仍然需要业务建模、需求、分析、设计这些工作流。

判断口号是否有用：

- “只做最重要需求”必须回答如何判断重要。
- “分离变和不变”必须回答如何识别变化点。
- “快速试错”不能替代对愿景、涉众利益和核心域机制的思考。

### 1.5 什么系统需要建模

只要要在市场或组织中获得价值，就有建模成本和收益的问题。不要用“系统小”“内部系统”“互联网产品”“遗留系统”“二次开发”作为免建模理由。

真正的问题不是“要不要建模”，而是“哪些工作流值得显式建模到什么程度”。

## 2. 业务建模之愿景

### 2.1 愿景定义

愿景：在目标组织代表看来，引进该系统应该给目标组织带来的改进。

基本格式：

```text
系统：
目标组织：
老大：
目标（度量指标）：
```

愿景回答两个问题：

- 这个系统最应该卖给谁。
- 它给这个人代表的组织或人群带来什么可度量改进。

愿景是需求排序的主要依据。

### 2.2 目标组织和老大

目标组织：待引入系统将改进其流程的组织，可以是机构，也可以是人群。

老大：目标组织的代表，是系统最优先照顾其利益的人。

定位时按三类情况处理：

| 情况 | 系统改进范围 | 定位步骤 |
| --- | --- | --- |
| 针对人群的非定制系统 | 某个人群 | 定位目标人群，再定位老大 |
| 针对特定机构的定制系统 | 某个机构 | 定位机构范围，再定位老大 |
| 针对某类机构的非定制系统 | 某类机构 | 定位机构范围、目标机构，再定位老大 |

定位目标人群时持续追问：

- 谁比谁更像目标人群？
- 为什么？
- 哪个细分人群更需要这个产品？
- 哪个代表最能体现该人群的关键痛苦？

定位机构范围时持续调整：

- 如果圈内大多数流程和改进无关，范围可能太大。
- 如果很多要改进的流程在圈外，范围可能太小。
- 老大的职权范围必须覆盖改进范围。

### 2.3 老大的常见误判

常见错误：

- 把目标机构的 IT 主管当老大。除非改进的是 IT 部门流程，否则 IT 主管只是接口涉众。
- 把机构之上的大领导当老大。大领导关注的指标太宏观，无法直接指导特定系统需求。
- 谁出钱谁是老大。出钱者是涉众，不一定是目标组织代表。
- 把能接触到的有权者当老大。能接触不等于最该优先满足。
- 虚构老大或只选择身边方便调研的人。定位应服务竞争和改进，不应服务调研便利。
- 把自己当老大。除非自己确实代表目标人群，否则“吃自己的狗粮”会污染需求。

### 2.4 提炼改进目标

改进目标是“系统改善组织行为的指标”，不是系统功能。

像目标的表达：

- 提高回访订单转化率。
- 减少每张订单处理人力。
- 缩短评估贷款风险周期。

不像目标的表达：

- 建立 CRM 系统。
- 提供自助下单功能。
- 能够对贷款申请做风险评估。

目标要求：

- 来自老大视角。
- 可度量。
- 是系统能带来的恰当改进，不是“赚钱更多”“升官更快”这种过大的目标。
- 可以有多个目标，但要排序，处理目标冲突。

提炼方法：

- 针对形容词追问度量，例如“规范”具体如何衡量。
- 从初步解决方案倒推：没有它，涉众付出什么代价？
- 借鉴目标组织已有 KPI。
- 用原因分析定位系统能影响的问题层级。

## 3. 业务建模之业务用例图

### 3.1 组织的两个视角

组织外观：对外提供价值的集合，可用业务用例图表示。

组织内观：内部系统的集合，包括人脑系统和非人智能系统，可用业务序列图表示。

软件系统只是组织的一个零件。引入软件的本质是把某些责任从现有业务工人或业务实体转移到新的业务实体。

### 3.2 业务执行者、业务工人、业务实体

业务执行者：在目标组织之外，与目标组织交互的人群或机构。

业务工人：目标组织内部的人脑系统。

业务实体：目标组织内部的非人智能系统。

判断边界看责任，不看物理位置、社保关系或办公地点。

识别业务执行者：

- 把焦点放在组织边界。
- 观察边界外哪些人群或机构和组织交互。
- 个人背后通常代表机构或人群，要提升到一致的抽象级别。
- 时间不是组织的业务执行者，应看成某个外部组织派来的接口系统。

### 3.3 业务用例

业务用例：业务执行者希望通过和目标组织交互获得的价值。

业务用例代表组织对外价值，不随内部岗位、人员、软件系统变化而变化。变化的是实现业务用例的业务流程。

识别业务用例的两条路线：

1. 从业务执行者出发，思考它和组织交互的目的。
2. 从组织内部活动出发，持续问“为什么”，向外追溯到外部业务执行者。

### 3.4 价值判断

价值是期望和承诺的平衡点。

例：以医院为研究对象，“挂号”通常不是患者要买的价值，“看病”才是；以挂号室为研究对象，“挂号”才可能是用例。

判断问题必须先明确研究对象。用例图应尽量画边界框或至少注明研究对象。

### 3.5 业务用例常见错误

错误一：把业务工人的行为当业务用例。

- “医生诊治”“收费人员收费”是组织内部解决方案。
- 业务用例应从外部执行者的价值看。

错误二：业务用例随待引入系统伸缩。

- 不能把臆想系统功能直接当业务用例。
- 业务用例是组织价值，不是某个将开发系统的功能清单。

错误三：把关心的流程片段提升为业务用例。

- 药师盘点、保洁、团队建设等内部活动应归入某个业务用例的基本路径或扩展路径。
- 组织内部一切零件都应从组织价值解释。

错误四：管理型业务用例。

- “提高利润”“加强管理”“提高效率”不是业务用例，容易和愿景或涉众利益混淆。

## 4. 业务建模之业务序列图

### 4.1 为什么用序列图描述业务流程

文本适合精确描述系统用例，但描述业务流程不够直观。

活动图常见问题：

- 容易只画人或部门，忽略非人智能系统。
- 容易描述动作，弱化责任分配。
- 过于灵活，容易掩盖流程认识不足。

业务序列图的优势：

- 把人脑系统和非人系统平等看待。
- 用对象协作实现用例的思想贯通业务建模和系统建模。
- 消息强迫建模人员思考“谁承担什么责任”。

### 4.2 业务序列图规则

消息代表责任分配，不代表数据流。

```text
A -> B: 审批报销单
```

含义是 A 请求 B 承担“审批报销单”责任，而不是报销单数据从 A 流到 B。

抽象级别是系统之间的协作：

- 生命线最小颗粒是系统，包括人脑系统和非人智能系统。
- 不要把数据库表、界面控件、组件等内部设计放进业务序列图。
- 不要把业务执行者和目标组织整体直接搬进业务序列图；要展开组织内部系统协作。
- 无智能的纸张、申请单只能作为消息参数，不能作为生命线。

只画核心域相关系统：

- 如果某外部软件只是通用工具，且不影响核心域改进，可不画。
- 如果它对当前核心流程改进有意义，应画出来。

时间作为特殊业务实体：

- 时间可触发某些业务事件。
- 时间是外系统，定时器是其他系统用来和时间交互的边界设施。

责任必须分配给有能力承担的业务对象：

- Word 不能“写标书”，工作人员才理解“标书”。
- 工具只承担其领域内能承担的责任。

### 4.3 现状业务序列图

现状就是当前真实发生的流程，不是理想流程、规范流程或开发团队介入前的流程。

常见错误：

- 把想象中的改进当现状。
- 把现状误解为纯手工流程。
- 把本开发团队介入前当现状。
- 把组织规范当真实现状。
- 认为创新产品没有现状。只要要替代老大头脑中的某种现有选择，就有现状。
- 认为做通用产品没有现状。应选典型目标组织或目标人群观察其现有行为。

### 4.4 改进业务序列图

在真实现状上寻找改进点，再画改进后的业务序列图。

三种主要改进模式：

1. 物流变信息流：提炼物承载的信息，用软件传递信息，减少物和人的移动。
2. 改善信息流转：减少人在多个系统之间搬运信息，让软件系统协调软件系统。
3. 封装领域逻辑：把人脑中的判断、计算、经验提炼并封装到软件中。

补充思考方法：

- 先假设资源充足，构造理想方案。
- 再用现有资源做低成本替代方案。
- 目标是突破“做不了”的思维限制，再回到现实折中。

### 4.5 从业务序列图推导系统需求

改进业务序列图中，指向待引入系统的外部消息，通常映射为系统用例。

这条路径比拍脑袋列功能稳定：

```text
愿景 -> 业务用例 -> 现状业务序列图 -> 改进业务序列图 -> 系统用例
```

## 5. 需求之系统用例图

### 5.1 系统执行者

系统执行者：在所研究系统外，与系统发生功能性交互的其他系统。

要点：

- 系统是能独立对外提供服务的整体。
- 系统边界是责任边界，不是物理边界。
- 执行者必须和系统发生功能性交互。
- 执行者是否重要无关紧要；重要性属于涉众排序问题。
- 执行者可以是人，也可以是非人系统，也可以是时间。

不要把以下对象误判为执行者：

- 比实际操作者更重要但不直接交互的人。
- 鼠标、操作系统等非功能交互对象，除非所研究系统的核心功能就是和它交互。
- 仅观看系统输出、但用例不等待其响应的人。

从业务序列图映射执行者：

- 与所研究系统有实线消息交互的外部对象，映射为系统执行者。

### 5.2 系统用例

系统用例：系统能够为执行者提供的、涉众可以接受的价值。

判断标准仍是“买卖平衡点”：

- 执行者愿意用系统做某事。
- 系统能承诺完成某个有价值目标。
- 涉众能接受该目标达成方式和约束。

常见非用例：

- 登录：通常只是其他用例的交互片段。
- 输入密码、点击按钮、打开页面：通常是步骤或交互设计。
- 刻字、乱点、误用：这些是用户可能发生的行为，但不是系统承诺交付的价值。
- “管理 X”：通常是从设计或数据表反推的伪用例。

### 5.3 CRUD 和复用错误

“新增、修改、删除、查询”如果只是从数据库表或模块设计映射出来，多半不是合格用例。

正确思路：

- 找业务流程中为什么需要新增、修改、删除、查询。
- 不同执行者、不同涉众利益、不同业务目的，可能是不同用例。

不要为了实现复用合并用例。

- 用例是系统对外可卖的用法。
- 设计可以复用，需求不追求复用。
- 若多个执行者指向同一用例，要检查：是否应抽象出共同执行者，或拆成多个用例。

### 5.4 系统用例没有层次

系统用例研究的是某个特定系统，不是组织，也不是系统内模块。

错误做法：

- 把组织价值当系统“高层用例”。
- 把愿景当用例。
- 为“模块”“子系统”画用例图。
- 把用例包误认为系统内部模块。

用例很多时可以分包，但包里的用例仍然是系统用例，不是包或模块的用例。

### 5.5 用例命名

用例名通常用动宾结构，例如：

- 取现金
- 创建公开课
- 查看当天名单

避免弱动词和空泛词：

- 不写“进行发票作废”，写“作废发票”。
- 不写“管理学生”，应分解为执行者真正要达成的价值。

### 5.6 主执行者和辅执行者

主执行者：主动发起用例。

辅执行者：用例执行过程中被系统请求协作，若无响应会影响用例目标。

不要把以下对象当辅执行者：

- 可能使用用例产出信息的人。
- 曾经提供用例所需信息的人。
- 只是被通知、系统不等待其响应的人。

一个外系统可以在某个用例中是主执行者，在另一个用例中是辅执行者。不要说“某某是系统的主执行者”，应说“某某是某用例的主执行者”。

## 6. 需求之系统用例规约

### 6.1 用例规约内容

用例规约以用例为核心组织需求内容。写了合格用例规约，可以不再另写一套需求规约。

基本内容：

- 用例名
- 执行者
- 前置条件
- 后置条件
- 涉众利益
- 基本路径
- 扩展路径
- 补充约束：字段列表、业务规则、质量需求、设计约束

### 6.2 前置条件和后置条件

前置条件：用例开始前，系统需要满足的约束。

后置条件：用例成功结束后，系统需要满足的约束。

规则：

- 必须是系统能检测的状态。
- 前置条件必须在用例开始前可检测。
- 写状态，不写动作。
- 使用核心域词汇。
- 不写“系统正常运行、网络正常”这类通用废话。
- 后置条件不要写“某某成功”，要写系统承诺达到的状态。

“已登录”通常不应作为前置条件。登录通常是多个用例共享的交互片段，可作为被包含用例或在规约步骤中处理，但不要把它误当系统对外价值。

### 6.3 涉众利益

涉众利益决定路径怎么走。

涉众利益是某类人针对某件事：

- 希望什么。
- 担心什么。
- 哪些权益可能受损。

寻找涉众来源：

1. 人类执行者。
2. 上游资源提供者。
3. 下游结果使用者或受影响者。
4. 信息的主人。

研发团队成员不是所开发系统的涉众。按“投币法”思考：系统像投币购买来的成品，研发团队不存在。

写涉众利益要具体，不要写“担心出错”这种放之四海而皆准的话。应写清楚担心哪类错、为什么会错、错了损害谁。

### 6.4 基本路径

基本路径：执行者和系统交互最顺利、一路达到后置条件的场景。

步骤按交互回合写。每个回合包括：

- 请求：主执行者请求系统做某事。
- 验证：系统验证输入或状态。
- 改变：系统改变自身状态或保存信息。
- 回应：系统反馈结果，或请求辅执行者协作。

一个回合必须有请求，并且至少有验证、改变、回应中的一类。

书写规则：

- 只写系统能感知和承诺的内容。
- 用主动句理清责任。
- 主语只能是主执行者或系统。
- 系统是黑箱，不写前端、后端、客户端、服务器、子系统之间的内部协作。
- 使用核心域术语。
- 不写界面细节，例如下拉框、文本框、按钮。
- 不写交互细节，例如每输入一个字符如何校验；只有涉众明确认为“不这样不行”时才作为需求，这种例外极少出现。
- 需求判断标准是“不这样不行”，不是“这样也行”。

错误示例与修正：

| 错误 | 问题 | 修正 |
| --- | --- | --- |
| 会员保存订单 | 责任不清 | 会员提交订单信息；系统保存订单 |
| 会员查询商品 | 查询发生在系统 | 会员提交查询条件；系统查询商品；系统反馈结果 |
| 系统自动计算 | “自动”冗余 | 系统计算 |
| 会员手动输入 | “手动”冗余 | 会员输入 |
| 系统显示订单信息 | 界面词 | 系统反馈订单信息 |

### 6.5 扩展路径

扩展路径：基本路径某步骤发生系统需要处理的意外时，系统处理该意外的路径。

编号建议：

```text
2a. 账户号码不合法：
2a1. 系统反馈账户号码不合法
2a2. 返回1
```

扩展常见来源：

- 验证步骤不通过。
- 请求辅执行者协作时无响应或返回异常。

谨慎处理：

- 系统无法感知或不负责处理的意外，不是扩展。
- 设计、编码、数据库、网络等实现故障，不应作为普通扩展路径；可靠性需求写在质量需求中。
- 不引起交互行为变化的选项，不是扩展，应写字段列表或业务规则。
- 界面跳转到其他用例，不是本用例扩展。

### 6.6 补充约束

补充约束绑定路径步骤，编号表示绑定的步骤，不表示执行顺序。

如果约束作用于整个用例，可用 `*` 编号。

#### 字段列表

字段列表描述某步骤中领域概念的组成。

示例：

```text
1. 注册信息 = 公司名 + 联系人 + 电话 + {联系地址}
1. 联系地址 = 州 + 城市 + 街道 + (邮编)
*. 客房状态 = {空闲 | 已预定 | 占用 | 维修中}
```

字段列表不是数据库模型，也不是越细越好。写到涉众有共识即可。

#### 业务规则

业务规则描述系统运算或判断规则。

规则：

- 可以用自然语言、公式、决策表、决策树表达。
- 业务规则不是实现算法。
- 若写成某算法、某框架、某存储方案，要问“不这样行吗”，找背后的真正需求。

#### 质量需求

质量需求描述系统把事做正确之外，还要达到的指标。

常见类型：

- 可用性：人类执行者和系统交互质量，例如平均 5 次操作内完成入住。
- 性能：速度、容量、能力，例如 0.5 秒内拍照、允许 1000 人同时使用。
- 可靠性：平均无故障时间、平均修复时间。
- 可支持性：升级、修复、维护能力。

质量需求必须可度量。不要写“简单易用”“高性能”“稳定可靠”这种不可验证词。

#### 设计约束

设计约束是在实现时必须遵守的限制，例如平台、语言、报表格式、界面样式。

设计约束也是需求，但必须来自涉众视角。来自开发人员偏好的“三层架构”“面向对象”“分三个页面”等通常是假需求，要追问背后的质量需求。

## 7. 需求启发

### 7.1 需求启发的定位

需求启发是获取需求素材的工作。需求不是现成蘑菇，不能只是“采集”。需求人员要发现、追问、观察、判断。

两个障碍：

- 知识的诅咒：懂的人难以想象不懂的人怎么想。
- 做和定义不同：涉众会做，不代表能定义和讲清楚。

### 7.2 模型和视图分离

开发团队内部使用模型，例如 UML。

和涉众交流使用视图，例如：

- 给高层看愿景和指标。
- 给中层看文档和流程。
- 给一线看局部原型、样例、表单。
- 对不愿看材料的人，用访谈和观察。

不要为了迁就涉众而降低模型严谨性。交流形式可以多变，团队内部模型应稳定。

### 7.3 和涉众谈利益，不直接要需求

涉众没有资格单独决定需求，也没有责任提供需求。

需求人员应：

- 提炼涉众背后的利益。
- 平衡不同涉众利益。
- 把涉众提出的解决方案还原成问题和利益。
- 不抱怨涉众“说不清需求”。

### 7.4 需求启发手段

研究资料：

- 先获取核心域初步知识，再去访谈和观察。
- 资料包括工作手册、行业规范、表格、文件、日志、邮件、现有系统及文档。
- 优先研究实际使用中的资料，不只看空白模板。
- 阅读时同步记录领域类图、业务序列图、疑问和假设。

问卷调查：

- 主要用于给人群分类、挑选样本。
- 适合产品型系统早期定位。
- 可设置明显题目识别敷衍答卷。

访谈：

- 选择真正代表某类涉众的人，不要用主管替代一线岗位。
- 经验丰富的“老师傅”很重要，即使他不懂电脑或不支持信息化。
- 有利益冲突的涉众尽量分开访谈。
- 记录方式可用笔记、录音、录像；访谈记录必须回看和使用。

访谈问题聚焦业务流程和涉众利益，而非直接问系统功能：

- 这个工作需要哪些材料，谁提供？
- 这个工作产生什么结果，谁关注？
- 这件事最烦的是什么？
- 做不好会影响谁？
- 为什么要这样做？

观察：

- 在涉众工作现场观察或亲身体验。
- 关注时间、操作次数、错误、混乱、等待、重复搬运信息。
- 观察环境约束，例如光线、噪声、手是否空闲、网络状况。

研究竞争对手：

- 不是对手有什么就加什么。
- 要判断战场位置和竞争策略。
- 领先者重在防御并扩张品类；追赶者攻击领先者强势背后的弱点；侧翼者聚焦细分特色；弱者应尽快形成专家型定位。

### 7.5 需求人员能力

核心能力：

- 好奇心：对陌生事物感兴趣，并能从熟悉中发现异常。
- 探索力：从信息碎片归纳真正问题。
- 沟通力：和涉众、不同涉众之间、涉众与开发人员之间协调。
- 表达力：用自然语言清楚组织需求内容。
- 热情：愿意持续深入第一线，直到找到真正问题。

## 8. 分析

### 8.1 核心域和非核心域

一个软件系统封装多个领域的知识。代表系统竞争力、让系统区别于其他系统的领域是核心域；其他领域是非核心域。

例：

- 文档处理器核心域：文档、页、行、字。
- 电商系统核心域：商品、订单、会员。
- 非核心域可能是 GUI、数据库、网络协议、框架、文件系统。

分析工作的重点是核心域。非核心域改进必要但不充分，因为竞争对手也能买到或学到相同工具。

### 8.2 分离核心域和非核心域

分离原因：

- 人脑容量有限。
- 核心域和非核心域混杂会让复杂度从相加变成相乘。
- 同一核心域可能映射到多个平台和实现。
- 分析模型应先表达核心域机制，再在设计中映射到数据库、界面、代码和部署。

实践原则：

- 分析类图不放数据库主键、外键、表结构实现细节。
- 不把集合、链表、栈等实现结构当核心域术语。
- 不在核心域类图中引入平台类，除非所研究系统核心域就是该平台。

### 8.3 三种分析类

分析工作流假设系统内部有三种类：

| 类型 | 责任 | 和用例关系 | 命名 |
| --- | --- | --- | --- |
| 边界类 | 输入、输出、简单过滤 | 每个有接口的外系统映射一个边界类 | 外系统名称 + 接口 |
| 控制类 | 控制用例流、分解和分配责任 | 每个用例可映射一个控制类 | 用例名称 + 控制 |
| 实体类 | 封装核心域逻辑和数据 | 用例和实体类多对多 | 领域概念名 |

要点：

- 外系统包括执行者，也包括仅接收系统输出的信息接收者。
- 边界类不暗示图形界面、窗体或 API 形式。
- 控制类可选；如果只传话，没有分解和分配责任，可去掉。
- 实体类识别最难，应投入主要思考。
- 系统执行者和实体类没有必然对应关系；系统要记住某概念，才需要实体类。

三类协作套路：

```text
执行者 -> 边界类 -> 控制类 -> 聚合根/实体类 -> 其他实体类
```

反馈通常由边界类完成。

### 8.4 识别分析类和属性

从用例规约的基本路径、扩展路径、字段列表、业务规则中，找表示名词或事件的词汇，逐个判断：

- 系统是否要记住这个概念？
- 它是类，还是某个类的属性？
- 它是否属于核心域？

关系数据库经验可辅助思考：

- 表约等于类。
- 列约等于属性。
- 行约等于对象。
- 外键关系约等于关联。

但分析类图不是数据库模型，不应直接塞入主键、外键和实现类型。

### 8.5 示例：从用例规约提炼类和分析序列图

下面用一个短例子展示从用例规约到实体类、属性、关联，再到分析序列图责任分配的过程。

用例规约片段：

```text
用例名：预订仓位
执行者：游客

基本路径：
1. 游客选择航线、航期
2. 系统反馈该航期可选仓位
3. 游客选择仓位
4. 系统验证该仓位可以预订
5. 系统保存仓位预订
6. 系统反馈预订成功

字段列表：
1. 航期 = 航线 + 出发日期 + 船舶
2. 可选仓位 = 仓位号 + 层 + 价格 + 状态
5. 仓位预订 = 游客 + 航期 + 仓位安排 + 预订时间

业务规则：
4. 可预订规则：仓位安排属于所选航期，状态为空闲，且未被其他有效预订占用。
```

逐项提炼：

| 规约词汇 | 判断 | 模型结果 |
| --- | --- | --- |
| 游客 | 是执行者；如果系统要保存预订人信息，也是实体类 | `游客` 或更贴近领域的 `预订人` |
| 航线 | 系统需要记住并供选择 | 实体类 `航线` |
| 航期 | 带出发日期和船舶，是一次可售事件 | 实体类 `航期`，关联 `航线` |
| 可选仓位 | 动态筛选结果，不是稳定领域对象 | 不建类；它是当前时刻满足“航期匹配、状态空闲、无有效预订”的 `仓位安排` 集合 |
| 仓位 | 船舶或舱室中的物理位置 | 若系统要维护仓位基础信息，建实体类 `仓位` |
| 仓位安排 | 某航期开放销售的仓位及价格、状态 | 实体类 `仓位安排`，关联 `航期` 和 `仓位` |
| 可以预订 | 判断规则，不是类 | 放入业务规则或实体责任 |
| 仓位预订 | 记录一次预订事实，带预订时间 | 事件类 `仓位预订`，关联 `游客`、`航期`、`仓位安排` |
| 仓位号、层 | 直接描述物理仓位 | `仓位` 的属性，若“层”有平面图和规则，再分离为类 |
| 价格、状态 | 直接描述该航期上的可售安排 | `仓位安排` 的属性 |

得到的核心实体关系：

```text
航线 1 -- * 航期
航期 1 -- * 仓位安排
仓位 1 -- * 仓位安排
游客 1 -- * 仓位预订
航期 1 -- * 仓位预订
仓位安排 1 -- * 仓位预订
```

分析序列图的责任分配骨架：

```text
游客 -> 游客接口: 提交航线和航期
游客接口 -> 预订仓位控制: 准备可选仓位
预订仓位控制 -> 航期: 获取可选仓位安排
航期: 作为聚合根筛选自己的仓位安排
游客接口 -> 游客: 反馈可选仓位

游客 -> 游客接口: 提交仓位
游客接口 -> 预订仓位控制: 预订仓位
预订仓位控制 -> 航期: 验证所选仓位仍可预订
预订仓位控制 -> 仓位预订: 创建预订
游客接口 -> 游客: 反馈预订成功
```

检查点：

- `游客接口` 来自执行者，属于边界类。
- 请求方向通常是执行者向内发给边界类，反馈方向通常是边界类向外发给执行者。
- `预订仓位控制` 来自“预订仓位”用例，属于控制类；本例中“展示可选仓位”是预订用例的前段步骤，不单独拆成另一个用例。
- `航期` 在这里作为聚合根，遍历自己关联的 `仓位安排` 集合，并结合有效 `仓位预订` 筛选可选项。
- 预订前仍要再次验证所选仓位是否可预订，因为展示候选和提交预订之间可能发生并发占用。
- `航线`、`航期`、`仓位`、`仓位安排`、`仓位预订` 是实体类。
- “可选仓位”是动态筛选结果，不必直接建类。
- “可以预订”是规则或责任，不必直接建类。

### 8.6 命名规则

类名：

- 使用单数名词。
- 不带“类”“表”“数据”“信息”等冗余后缀，除非它们是领域术语。
- 使用一致词汇；同一概念不要同时叫宝贝、商品、产品。
- 使用核心域术语，不用自己熟悉的实现术语替代。

属性名：

- 不带类名冗余，例如 `顾客.顾客姓名` 应改为 `顾客.姓名`。
- 属性应直接描述类。
- 类型可以是基础类型或值对象，但不要过早映射到数据库类型。

### 8.7 切勿照猫画虎

常见错误：

类图长得像用例图：

- 看到“搜索商品”，就画 `顾客 -> 搜索 -> 商品`。
- 真正机制可能是商品类别、特征、规格、价格之间的关系。

类长得像过程：

- 把过程名加 `er` 或 `or` 变成类。
- 把原过程塞成类操作。
- 仍然是面向过程，只是换成类语法。

类长得像报表：

- 把报表每一列直接做成某个“大类”的属性。
- 报表通常是多个实体类属性的视图组合。

好的类封装领域概念及其内在规则，而不是需求文字、界面文字或报表栏目的逐字翻译。设计源于需求，但高于需求；不能把需求表象直接搬成设计。

### 8.8 核心域透镜

用核心域透镜看所有概念：

- PowerPoint、黑板、全息投影都可能映射为“演示工具”。
- 点击开始按钮、在纸上书写、语音开始都可能映射为“开始考试”。
- 向数据库答题表插入记录、在答卷涂黑一格都可能映射为“答题”。

目的：

- 把当前实现手段映射为更稳定的核心域概念。
- 避免被数据库、界面、协议、设备等非核心域细节牵着走。

### 8.9 属性检查规则

规则一：属性要直接描述类。

- “联系人的组织名称”隔着“组织”，应分出 `组织.名称`。
- 如果某属性实际属于关联对象或其他类，应移动。

规则二：分析类不放外键属性。

- `联系人.组织编码` 不应作为核心域属性。
- 联系人与组织应通过关联表达。

规则三：属性在本领域内不可再分解。

- 若分解后仍是本核心域概念，应分成类。
- 若分解后进入基础语义或非核心域，可保留为属性。

规则四：多重性大于 1 的属性应考虑分离。

- 电话1、电话2、电话3 应分离为 `联系方式`。
- 不要用逗号字符串或数组属性掩盖一对多关联。

规则五：属性对所有对象都有意义。

- 若属性只适用于部分对象，应考虑子类或关联。
- 状态属性应进一步用状态机或事件建模精化。

状态属性的处理顺序：

- 早期为了理解规则，可以临时写出 `正在生效`、`已通知`、`可预订` 这类状态属性。
- 继续追问“它为什么会变成这个状态、由哪个事件改变、改变后允许什么行为”。
- 如果状态转换有规则，就用状态机封装；如果系统需要记录发生事实，就建事件类，例如 `通知`、`仓位预订`。
- 精化后尽量删除可推导的状态属性。例如 `可选仓位` 可由 `仓位安排.状态` 和有效 `仓位预订` 推导；推导结果是在需要展示时实时查询状态为空闲且无有效预订的仓位安排，不必另存一个 `可选` 类或布尔属性。

规则六：大量对象有相同属性值时，考虑分离“描述”类。

- 多个设备共享品牌型号参数，应分出设备规格。
- 多次公开课共享主题、大纲，应分出课程。

### 8.10 类之间三类关系

类之间的关系：

- 泛化：集合关系，子类对象集合包含于超类对象集合。
- 关联：个体关系，一个对象和另一个对象有系统需要维护的关系。
- 依赖：如果 B 变化导致 A 需要变化，但二者没有泛化或关联，则 A 依赖 B。

区分泛化和关联：

- “人分男人和女人”是泛化。
- “人有手和脚”是关联。
- 不要只看自然语言里的“有”，要看集合关系还是个体组装关系。

### 8.11 识别泛化

三种思路：

1. 直接判断：A 是 B 的一种吗？B 是 A 的一种吗？
2. 自下而上：多个类有共同特征，抽象超类。
3. 自上而下：某类部分对象有特有属性或行为，分裂子类。

注意：

- 子类应能替换超类，不能削弱超类契约。
- 尽量不要跨领域使用泛化，不要为了复用 List、Map 等实现结构把它们拉进核心域类图。

### 8.12 识别关联

只有系统要维护的关系才是关联。世界万物总能找到关系，但系统只关注其中一小部分。

识别时检查：

- 系统是否需要记住这两个对象之间的关系？
- 关系是否有领域含义？
- 是否需要关联类记录事件、时间、状态或属性？
- 关联两端多重性是什么？
- 是否需要角色名、关联名、导航方向？

关联名和角色名：

- 模型要能讲出领域故事。
- 两个类之间有多种关联时必须使用角色名区分。
- 角色名在实现中常映射为变量名。

导航方向：

- 初期不确定可先双向。
- 理解深入后尽量改成单向，减少循环访问。
- 方向取决于领域责任，不是绘图美观。

多重性：

- 多重性是某一时间点快照下的关系数量。
- 不要把历史次数当当前多重性。一个人一生可能多次结婚，但在合法一夫一妻的领域规则下，某个时间点的“夫妻”关联仍是 `0..1` 对 `0..1`；如果要表达历史，应另建 `婚姻` 事件或 `前配偶` 关系。

自反关联：

- 同一类对象之间的关联。
- 可表达网、树、队列、环等结构。
- 常用于简化复杂泛化层次或关系类型。

### 8.13 聚合和组合

聚合、组合是特殊关联。使用出发点是责任分配，不是自然语言能不能说“A 有 B”。

聚合/组合的作用：

- 把一组协作频繁的类封闭起来。
- 外部对象先把消息发给整体，再由整体分配给部分。
- 相当于给类图分区，找聚合根。

组合比聚合更强：

- 整体销毁，部分也销毁。
- 部分只属于一个整体。
- 整体负责部分创建和销毁。

没有足够证据时，优先用普通关联，不要滥用聚合/组合。

### 8.14 彩色建模

彩色建模把领域类归为四种架构型，用来提示建模思路。

| 架构型 | 含义 | 特征 |
| --- | --- | --- |
| 事物 PartyPlaceThing | 系统围绕其状态变化展开的关键概念 | 状态丰富，领域事件发生在其身上 |
| 描述 Description | 决定事物规则和规格的概念 | 对象少，封装规则，状态变化不重要 |
| 时刻时段 MomentInterval | 带时间属性的事件类 | 对象多，记录发生过的事实，不应随意修改 |
| 角色 Role | 事物参与事件时扮演的角色 | 解耦事物和事件，可显式类或隐式角色名 |

常见关系：

- 时刻时段发生，事物们以不同角色参与。
- 事物变化规律由描述决定。

使用方式：

- 从时刻时段开始，找角色和事物。
- 从描述之间的规则关系开始，再添加事物。
- 同一类在不同上下文中颜色可能不同。
- 颜色只是提示，不要生搬硬套。

### 8.15 模式

模式不等于 GoF 23 设计模式。不同工作流、不同核心域、不同平台都有模式。

学习重点：

- 当前项目核心域的分析模式。
- 当前实现平台相关的设计和架构模式。
- 不要只盯通用设计模式。

### 8.16 泛化和关联转换

改变抽象级别时，泛化可转成更抽象类之间的关联。

例：

- “人分为男人和女人”是泛化。
- “人有性别”是关联或属性。

选择依据：

- 若重点是统计、记录和分类，关联或属性可能足够。
- 若重点是行为变异，泛化可能更合适。

很多分析模式通过把泛化转为关联来降低类结构变化成本。

### 8.17 人员模式

以下以人员管理这个常见领域模式为例，展示多值属性分离、泛化转关联、自反关联和规则下沉等分析技能如何组合使用。

人员信息常见变化点：

- 电话、邮箱、微信等联系方式可能多值。
- 联系方式类型会新增、废弃和改变。
- 联系方式有用途、合法性规则、绑定关系。用途用于区分同一人的多个联系方式为什么同时存在，例如办公电话、私人手机、收款邮箱。

改进模型：

- `人员` 关联多个 `联系方式`。
- `联系方式` 关联 `联系方式类型`。
- `联系方式类型` 可保存验证规则，例如正则表达式。
- `联系方式` 可关联 `用途`。
- 联系方式绑定要区分两个层次：`联系方式类型` 之间的“允许绑定”是规则层的自反关联，例如手机号可绑定微信；具体 `联系方式` 之间的“实际绑定”是实例层的自反关联，例如某个手机号实际绑定某个微信号。不要把规则层和实例层合并。

人员关系模式：

- 人与人之间的关系可用 `人员` 自反关联表达。
- 当关系类型很多时，引入 `人际关系类型`，把多个自反关联合并为一个带类型的关系。
- 关系约束，例如性别、年龄、组织限制，应放到关系类型或业务规则中。

## 9. 最小执行清单

做一个系统需求和分析时，按以下顺序推进：

1. 定位目标组织和老大，见 2.2。
2. 写愿景：系统、目标组织、老大、可度量改进目标，见 2.1 和 2.4。
3. 画业务用例图：组织对外提供什么价值，见 3.2 到 3.5。
4. 画现状业务序列图：真实流程中哪些人脑系统和非人系统协作，见 4.2 和 4.3。
5. 找改进点：物流变信息流、改善信息流转、封装领域逻辑，见 4.4。
6. 画改进业务序列图：待引入系统承担哪些责任，见 4.4。
7. 从改进业务序列图映射系统执行者和系统用例，见 5.1 到 5.6。
8. 为高优先级用例写用例规约，见 6.1 到 6.6。
9. 从用例规约提炼实体类、属性、关联、泛化，见 8.3 到 8.5、8.10 到 8.13。
10. 用属性规则、核心域透镜、彩色建模和常见模式精化类图，见 8.8、8.9、8.14 到 8.17。

每一步都问：

- 当前研究对象是谁？
- 这是组织价值、系统价值、核心域机制，还是实现方案？
- 这是涉众“不这样不行”的需求，还是开发人员觉得“这样也行”的设计？
- 这个概念属于核心域，还是非核心域？
