# 背景

我想用潘加宇的《软件方法》所讲述的方法学来开发系统，目前正在描述需要改进的现状业务流程。

# 任务

请从一段关于\[公寓出租]业务流程的语音素材提炼出业务流程，并使用序列图描述。

# 所输入信息的规范

一段语音素材。

# 要求输出信息的规范：

输出UML序列图，用PlantUML格式表达。在结尾附上你如何利用附件的参考资料上的知识提炼类和消息的详细思考过程。

# 约束和建议做法

我希望你按照以下思路来思考：

\*先分析所要求输出格式，确保满足要求。

\*识别流程描述中的人脑系统，建模为"业务工人" 构造型的类。

\*识别流程描述中的非人智能系统，建模为"业务实体" 构造型的类。

\*构造序列图，在序列图上安排所识别的业务工人、业务实体的实例。

\*识别流程描述中的行为，思考这个行为怎样能理解成"A请求B做某事"的形式，在序列图上添加A指向B的消息，消息名称为"做某事"。在识别行为的时候，要注意不要忽略人或非人智能系统自身思考或行动的行为。

我所给的素材可能有一定程度的散乱，需要你认真整理其中的责任分配。

# 示例

**例如，我提供的输入信息为：**

每隔一段时间，老师判断此时应该进入做题环节，老师请求做题软件出题，做题软件反馈题目信息，老师请求抽奖软件抽取学员。抽奖软件抽取学员之后，（通过发出声音）提醒被抽中学员回答问题。学员翻看手上的书和笔记，用自己平板电脑上的一款绘画软件Paint手写答案，然后展示答案。

**你的思考应该如下：**

首先，识别所输入信息中提到的人，它们将被建模成构造型为"业务工人"的类。可以识别出：老师、学员。我们不需要表达类，只需要在序列图上表达类的实例。于是得到PlantUML脚本：

participant ":老师" as aTeacher <<业务工人>>

participant ":学员" as aStudent <<业务工人>>

接下来，识别所输入信息中提到的非人智能系统，它们将被建模成构造型为"业务实体"的类。可以识别出：时间、做题软件、抽奖软件、Paint。“时间”被识别为一个悬挂在宇宙中的非人智能系统（业务实体）。定时发生的事情，可以建模为由“时间”向业务工人或业务实体发消息。同样，不需要表达类，只需要在序列图上表达类的实例。于是继续得到PlantUML脚本：

participant ":时间" as aTime <<业务实体>>

participant ":做题软件" as aQuizSoftware <<业务实体>>

participant ":抽奖软件" as aRaffleSoftware <<业务实体>>

participant ":Paint" as aPaint <<业务实体>>

注意，书和笔记是非智能系统，在此处不能识别为业务实体。即使是电子书或电子笔记，也不是智能系统。作为非人智能系统，可以被识别为业务实体的是电子阅读器软件，但所输入消息并未提到。

还要注意participant 名称中的冒号，例如":老师"，表示这是一个实例（Instance），不是类元（Classifier）。

接下来，我们逐句提炼：

（1）每隔一段时间，老师判断此时应该进入做题环节

可理解成"时间请求老师判断此时应该进入做题环节"，所以序列图上应该有消息"判断此时应该进入做题环节"，从":时间"指向":老师"，也就是说，是一个自反消息。像这样的人自身思考或行动的消息很容易被忽略，所以你提炼的时候要重视这个内容。于是继续得到PlantUML脚本：

aTime -> aTeacher : 判断此时应该进入做题环节()

（2）老师请求做题软件出题

可理解成"老师请求做题软件出题"，所以序列图上应该有消息"出题"，从":老师"指向":做题软件"。于是继续得到PlantUML脚本：

aTeacher -> aQuizSoftware : 出题()

（3）做题软件反馈题目信息

可理解成"做题软件请求做题软件反馈题目信息"，所以序列图上应该有消息"反馈题目信息"，从":做题软件"指向":做题软件"，也就是说，是一个自反消息（即自己指向自己的消息）。于是继续得到PlantUML脚本：

aQuizSoftware -> aQuizSoftware : 反馈题目信息()

（4）老师请求抽奖软件抽取学员

可理解成"老师请求抽奖软件抽取学员"，所以序列图上应该有消息"抽取学员"，从":老师"指向":抽奖软件"。于是继续得到PlantUML脚本：

aTeacher -> aRaffleSoftware : 抽取学员()

注意，在表达"A请求B做某事"的时候，我们只需要从A发消息到B，消息为"做某事"，并不需要从B返回消息到A。也就是说，不要有那种双双对对的消息。另外，消息已经代表了请求，所以消息名称只需要写"做某事"，而不是写"请求做某事"。

例如，老师请求抽奖软件抽取学员，像上面这样表达就可以，不需要抽奖软件又有一个消息"返回学员"指回到老师，如果这样画，反而是错的，因为这样画意味着"抽奖软件请求老师返回学员"。

（5）抽奖软件抽取学员之后，（通过发声音）提醒被抽中学员回答问题。

"抽奖软件抽取学员之后"，这一句不提炼任何内容。因为如果提炼成"抽奖软件请求抽奖软件抽取学员"就冗余了，因为前面的"老师请求抽奖软件抽取学员"已经表明":抽奖软件"在此处有"抽取学员"的责任，这就够了。也就是说，当自反消息的内容和引发自反消息的上一级消息内容相同时，忽略该自反消息。

"提醒被抽中学员回答问题"，可理解成"抽奖软件请求学员回答问题"，所以序列图上应该有消息"回答问题"，从":抽奖软件"指向":学员"。于是继续得到PlantUML脚本：

aRaffleSoftware -> aStudent : 回答问题()

此处需要注意，这种情况属于由业务实体请求业务工人做某事，也就是业务实体向业务工人发消息。碰到这样的情况要谨慎。如果要建模为业务实体向业务工人发消息，涉众（Stakeholder）必须急切等待业务工人响应该消息。例如，"抽奖软件提醒被抽中学员回答问题"这个场景中，老师这个涉众是急切等待着学员回应的，所以可以建模为"抽奖软件请求学员回答问题"。

如果老师并不急切等待，甚至学员都不在现场，抽奖软件在抽取学员之后，给学员发个了短信，那么可以提炼成"抽奖软件请求抽奖软件提醒被抽中学员回答问题"，对应PlantUML脚本为：

aRaffleSoftware -> aRaffleSoftware : 提醒被抽中学员回答问题() //注意，这一句对于本例子是不合适的。

（6）学员翻看手上的书和笔记

可理解成"学员请求学员翻看手上的书和笔记"，所以序列图上应该有消息"翻看手上的书和笔记"，从":学员"指向":学员"。于是继续得到PlantUML脚本：

aStudent -> aStudent : 翻看手上的书和笔记()

书和笔记不是人，也不是非人智能系统，不出现在序列图的生命线上。

（7）用自己平板电脑上的一款绘画软件Paint手写答案

此处不能建模为“aStudent -> aPaint : 手写答案()”，因为绘画软件Paint并不知道学员手写的内容是答案，它只知道学员手写或者绘画了，也就是说，在Paint软件内部的代码里面，应该没有“答案”的概念，只有线条等概念。正确的建模是：

aStudent -> aPaint : 手写(答案)

消息的名称只能是“手写”，“答案”作为消息的参数。

（8）展示答案

可理解成"学员请求学员展示答案"，所以序列图上应该有消息"展示答案"，从":学员"指向":学员"。于是继续得到PlantUML脚本：

aStudent -> aStudent : 展示答案()

**综上，得到本示例的序列图PlantUML脚本：**

participant ":老师" as aTeacher <<业务工人>>

participant ":学员" as aStudent <<业务工人>>

participant ":时间" as aTime <<业务实体>>

participant ":做题软件" as aQuizSoftware <<业务实体>>

participant ":抽奖软件" as aRaffleSoftware <<业务实体>>

participant ":Paint" as aPaint <<业务实体>>

aTime -> aTeacher : 判断此时应该进入做题环节()

aTeacher -> aQuizSoftware : 出题()

aQuizSoftware -> aQuizSoftware : 反馈题目信息()

aTeacher -> aRaffleSoftware : 抽取学员()

aRaffleSoftware -> aStudent : 回答问题()

aStudent -> aStudent : 翻看手上的书和笔记()

aStudent -> aPaint : 手写(答案)

aStudent -> aStudent : 展示答案()

可以按照消息的先后调整各个participant的从左到右的排列顺序，争取尽可能多的消息是从左指向右的，调整后的PlantUML脚本：

participant ":时间" as aTime <<业务实体>>

participant ":老师" as aTeacher <<业务工人>>

participant ":做题软件" as aQuizSoftware <<业务实体>>

participant ":抽奖软件" as aRaffleSoftware <<业务实体>>

participant ":学员" as aStudent <<业务工人>>

participant ":Paint" as aPaint <<业务实体>>

aTime -> aTeacher : 判断此时应该进入做题环节()

aTeacher -> aQuizSoftware : 出题()

aQuizSoftware -> aQuizSoftware : 反馈题目信息()

aTeacher -> aRaffleSoftware : 抽取学员()

aRaffleSoftware -> aStudent : 回答问题()

aStudent -> aStudent : 翻看手上的书和笔记()

aStudent -> aStudent : 展示答案()
