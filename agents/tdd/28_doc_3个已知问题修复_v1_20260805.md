## 问题一：`test_three_kingdoms.py` drop_all 清库导致 demo 种子数据丢失

### 1.1 现状

| 位置 | 调用点 | 行为 |
| :--- | :--- | :--- |
| `test_three_kingdoms.py:11` | `TestDatabaseSchema.setUpClass` | `init_database(drop_all=True)` — DROP 21 张表 |
| `test_three_kingdoms.py:55` | `TestResourceCRUD.setUpClass` | 同上 |
| `test_three_kingdoms.py:92` | `TestWarehouseCRUD.setUpClass` | 同上 |
| `test_three_kingdoms.py:134` | `TestThreeKingdomsDemo.setUpClass` | `scripts.init_db.main()` — 重建 + 三国数据 |

三个 `setUpClass` 均在全量跑完后将 DB 恢复为**仅含三国数据**，zhansan / liuming 账号全部消失。当前工作区依赖手动补种（见 `测试移交文档.md §3.1`）。

### 1.2 根因

`init_database(drop_all=True)` 执行 `DROP TABLE IF EXISTS ... CASCADE` 清掉全库表，再执行 `SCHEMA_SQL` 重建。`TestThreeKingdomsDemo.setUpClass` 调用 `scripts.init_db.main()` 只重建三国数据，不重建 demo/recording 种子数据。文件按字母序排在最后，全量跑完后 demo 数据必然消失。

### 1.3 修复方案

**方案：只在 `TestThreeKingdomsDemo`（最后一个类）的 `tearDownClass` 中补种，避免三次重复执行。**

四个类按字母序依次执行 setUpClass → 测试 → tearDownClass。前三个类各自触发 drop_all，但最后一个类 `TestThreeKingdomsDemo` 的 setUpClass 会再次 drop_all 并重建 schema。因此**只需在最后一个类的 tearDownClass 中补种一次**：

```python
class TestThreeKingdomsDemo(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        import sys, os
        sys.path.insert(0, os.path.join(os.path.dirname(__file__), ".."))
        from scripts.init_db import main
        main()

    @classmethod
    def tearDownClass(cls):
        """drop_all 清掉了 demo/recording 数据，自动恢复"""
        import subprocess, sys, os
        from pathlib import Path
        repo_root = Path(__file__).resolve().parents[2]
        env = {**os.environ, "PYTHONPATH": str(repo_root)}
        if os.getenv("DEMO_ZHANSAN_PASSWORD"):
            subprocess.run(
                [sys.executable, "scripts/seed_demo_data.py"],
                cwd=repo_root, env=env, capture_output=True
            )
        if os.getenv("DEMO_LIUMING_PASSWORD"):
            subprocess.run(
                [sys.executable, "scripts/seed_recording_data.py"],
                cwd=repo_root, env=env, capture_output=True
            )
```

前三个类（`TestDatabaseSchema`、`TestResourceCRUD`、`TestWarehouseCRUD`）的 `tearDownClass` **不加补种逻辑**，因为它们的 tearDown 后紧接着下一个类的 setUpClass 会再次 drop_all，补种无意义。

**设计要点**：
- 幂等：两个 seed 脚本本身幂等，单次调用无副作用。
- 环境变量缺失时静默跳过（与 seed 脚本行为一致）。
- 不修改 `src/` 代码，仅在测试文件内修复副作用。
- 比三个 tearDownClass 各补种一次节省约 2/3 的 seed 脚本执行时间。

**安全网**：在 `agents/tdd/conftest.py` 添加一个 session 级 fixture，在全套测试结束后检查 demo 账号（zhansan / liuming）是否存在，不存在则自动补种。作为兜底防止其他测试文件未来引入类似的 `drop_all` 副作用。

> **注意**：session fixture 的 yield 后代码只在正常 session 结束时执行。如果 pytest 被中断（Ctrl-C、crash），yield 后的代码不会执行。这是 pytest session scope 的已知限制，无法通过 try/finally 规避。在实际使用中，中断后手动补种即可，不影响正常 CI 流程。

```python
# agents/tdd/conftest.py
import os, subprocess, sys
from pathlib import Path

REPO_ROOT = Path(__file__).resolve().parents[1]

@pytest.fixture(scope="session", autouse=True)
def _ensure_demo_data_survives():
    """session 级安全网：全量跑完后确保 demo 种子数据存在。

    注意：yield 后代码只在正常 session 结束时执行。
    pytest 被中断（Ctrl-C / crash）时不会执行，需手动补种。
    """
    yield
    # 检查 zhansan 账号
    check_cmd = [
        sys.executable, "-c",
        "from src.db.database import get_db_connection; "
        "c = get_db_connection(); "
        "cur = c.cursor(); "
        "cur.execute('SELECT 1 FROM account WHERE login = %s', ('zhansan',)); "
        "print('EXISTS' if cur.fetchone() else 'MISSING'); "
        "cur.close(); c.close()"
    ]
    result = subprocess.run(check_cmd, cwd=REPO_ROOT, capture_output=True, text=True)
    if result.stdout.strip() == "MISSING" and os.getenv("DEMO_ZHANSAN_PASSWORD"):
        subprocess.run(
            [sys.executable, "scripts/seed_demo_data.py"],
            cwd=REPO_ROOT, env={**os.environ, "PYTHONPATH": str(REPO_ROOT)},
            capture_output=True
        )
    # 检查 liuming 账号
    check_cmd[3] = "liuming"
    result = subprocess.run(check_cmd, cwd=REPO_ROOT, capture_output=True, text=True)
    if result.stdout.strip() == "MISSING" and os.getenv("DEMO_LIUMING_PASSWORD"):
        subprocess.run(
            [sys.executable, "scripts/seed_recording_data.py"],
            cwd=REPO_ROOT, env={**os.environ, "PYTHONPATH": str(REPO_ROOT)},
            capture_output=True
        )
```

## 问题二：`test_chat_with_context` / `test_full_workflow` LLM 超时 504

### 2.1 现状

`src/routers/chat.py:81-91`：
```python
result = await asyncio.wait_for(
    asyncio.to_thread(_run_agent), timeout=30
)
# ...
except asyncio.TimeoutError:
    logger.error("Chat request timed out (30s)")
    raise HTTPException(504, "AI agent timed out. Is the LLM server running?")
```

FastAPI 30s 硬超时，LLM 延迟抖动时返回 504。

`test_three_kingdoms_http.py` 中相关用例：
```python
# line 551 (test_endpoint) — 断言宽限集不包含 504
assert resp.status_code in (200, 500, 503)  # 504 → FAIL

# line 564 (test_chat_with_context) — 同上
assert resp.status_code in (200, 500, 503)  # 504 → FAIL
```

`test_endpoint` 的断言宽限集 `(200, 500, 503)` 不包含 504，理论上 LLM 超时时会 FAIL。文档记录"已验证通过"可能是因为该用例发送的 `"hi"` 简短消息 LLM 很快返回，未触发 30s 超时。

`test_full_workflow`（line 582）走的是完整业务流（组织→人员→资源→仓库→交易→参与方），**不直接调用 `/chat`**，504 只影响两个 chat 用例。

### 2.2 根因

504 是已知可接受的超时结果（LLM 延迟抖动），但断言宽限集未包含 504，偶发 LLM 慢时会误报为测试失败。

### 2.3 修复方案

**方案：将两个 chat 用例的断言宽限集从 `(200, 500, 503)` 改为 `(200, 500, 503, 504)`。**

```python
# test_endpoint (line 551)
assert resp.status_code in (200, 500, 503, 504)

# test_chat_with_context (line 564)
assert resp.status_code in (200, 500, 503, 504)
```

**设计要点**：
- 504 是已知可接受的超时结果，加进去匹配实际行为。
- 不改 `src/` 代码，不改 30s 超时（这是合理的保护）。
- 仅修改断言宽限集，最小侵入。

**后续建议**（非本次修复范围）：504 是 LLM 延迟抖动的间接指标，建议在 CI 流程中单独统计 504 出现次数，作为 LLM 服务健康度的监控数据。

### 2.4 影响范围

- 修改 `agents/tdd/test_three_kingdoms_http.py` — 2 处断言
- 不影响 `src/`、不影响其他测试文件

## 风险与回滚

| 风险 | 概率 | 影响 | 缓解 |
| :--- | :--- | :--- | :--- |
| tearDownClass 补种失败（seed 脚本异常） | 低 | demo 冒烟仍失败 | seed 脚本本身有错误处理；conftest session fixture 作为二次安全网 |
| 504 宽恕掩盖真 LLM 故障 | 低 | 504 时不知道 LLM 真的挂了 | 504 只在 chat 用例中宽恕，其他路由不变；LLM 故障仍会体现在其他指标 |
| conftest session fixture 引入新的 fixture 冲突 | 低 | 全量测试中断 | fixture 名为 `_ensure_demo_data_survives`（下划线前缀，非测试用），scope=session，autouse，无参数 |
| conftest session fixture 在 pytest 中断时不执行 | 中 | 中断后 demo 数据需手动补种 | 正常 CI 流程不会中断；中断后手动补种即可，见 §1.3 注释 |
